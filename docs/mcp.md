# MCP server

The api worker serves ContentWorker's capabilities to agents over MCP, through the same use-cases,
scopes and validation as the HTTP API.

The MCP server is served by the api worker, at **`/mcp`** (`https://api.<domain>/mcp`, and on the
admin origin through the web gateway).
It is a **stateless streamable-HTTP** server built on the v2 TypeScript SDK
(`@modelcontextprotocol/server`): tools are defined one file per area in
`packages/http/src/mcp/tools/` and registered by `buildServer` (`packages/http/src/mcp/server.ts`),
and one shared handler (`packages/http/src/mcp/http.ts`, `createHandler`) serves both protocol eras:

- **2026-07-28** clients send self-contained requests with no `initialize` handshake. A fresh
  client makes its first call in two requests instead of four, and it caches `tools/list` for
  five minutes.
- **2025-era** clients get the stateless fallback: a fresh server for each request, as before.

Auth is a bearer token resolved like the HTTP API: the MCP root token (`MCP_TOKEN`), a hashed API
key, an OAuth access token, or a personal access token (`packages/http/src/mcp/routes.ts`). MCP mounts
only where the management surface does (`ROLE` includes `management`). On a persistent deployment
it also requires an explicit `MCP_TOKEN`; the in-memory store falls back to `dev-mcp-token`, and
`pnpm dev` sets `MCP_TOKEN=dev-mcp-token`, so a local client can connect to
`http://localhost:5173/mcp`. Every tool calls `authorize(principal, scope, space)`
before delegating to a use-case, and `space`/`environment` default to the seeded values when
omitted. Request bodies are capped at 32 MiB, which fits the importers' 20 MB payload limit after
JSON escaping. The SDK answers internal failures with a bare 500, so the worker logs them through
the handler's `onerror`.

**Errors and audit, once for every tool.** `buildServer` wraps `registerTool`, so every tool's
handler runs through one path. A failure that isn't a domain error becomes `Internal server
error` (`toolFailure`). A `ValidationError` is returned, not thrown, as an `isError` result whose
text is REST's 422 body (`toHttpError`): `{ "error": { "code": "validation_failed", "message",
"issues": [{ "field", "locale"?, "message" }] } }`, so an agent sees each field path
(`body[0].heading`). A `ForbiddenError` or `ConflictError` that carries details answers the same
way, as REST's 403 or 409 body: a stale `expectedVersion` gives
`{ "error": { "code": "conflict", "message", "details": { "currentVersion", "expectedVersion" } } }`,
which the admin reads when a save made through Coworker meets one. A successful call that changes something is recorded in the audit trail
(`auditToolCall`, `packages/http/src/mcp/audit.ts`) with the shape REST's `auditMiddleware` uses:
the actor (`auditActor`), action `MCP <tool>`, the space, the resolved environment when the tool
takes one, `targetId` from `id` / `apiId` / `alias`, `targetType` in REST's words
(`toolTargetType`), status 200, and the `detail` of what its saves changed
([Audit log](./api-reference.md#audit-log)); calls of one batch that may write take turns, so a row
holds only its own. A tool is a write unless it
declares itself a read, with the annotation `readOnlyHint: true` beside its schema; a
propose-or-apply tool is audited only when it applies (`apply: true`,
`createTasks: true`, no `dryRun`). Reads never write (one writer per database), and a failed audit
write never fails the call.

**Per-request cost.** Each request builds a server bound to the caller's principal, so building it
has to be cheap. Every tool's Zod input schema, and its JSON Schema conversion, is built once per
isolate and shared (`toolSchema` in `packages/http/src/mcp/tools/shared.ts`). Building a server takes about
0.1 ms; without the cache it took about 2 ms, and every `tools/list` added another millisecond. As
a consequence, **a tool's input schema must never depend on the principal or deps**;
authorization belongs in the handler. Who asks changes which tools are listed, never their shape.
`preloadSchemas()` runs at module scope, so the SDK's own
schemas are built during isolate warm-up rather than on the first request.

**Which tools a caller sees.** `tools/list` shows a tool when the caller holds any scope in its row of
`TOOL_SCOPES` (`packages/http/src/mcp/tool-scopes.ts`), and a tool in `UNSCOPED_TOOLS` is shown to any
caller, unless `DEPLOYMENT_TOOLS` keeps it from a caller bound to one space. A tool that checks several
scopes shows to a holder of any of them, so a caller can see a tool that needs more than it holds. A
key bound to one space sees 13 tools with delivery scopes, 81 with preview scopes and 242 with
management scopes; only a deployment-wide principal with every scope sees all 250. This only saves an agent context: every handler still authorizes,
and an unlisted tool stays callable and answers with the scope it needs. The admin's assistant lists
every tool once per isolate and narrows that per person, because `tools/list` itself depends on who
asks. A new tool adds its row, and `tool-visibility.test.ts` fails until
the table matches the `SCOPES` in the handler. A client may hold a list for five minutes, so a change
to a key's scopes can take that long to show.

**Agent instructions.** A content type's optional `agentInstructions` (plain text, at most 4,000
characters, set through `model_create_content_type` or `POST …/content-types`) are the model author's
style guidance for agents writing its entries. `model_get_content_type` returns them;
`model_list_content_types` leaves them out, and Delivery never serves them. They are data: they can't
authorize a tool call or a change to keys, webhooks, roles, functions or settings, and the tool's
description tells agents so. The ContentWorker assistant sees them only when it reads a type with
that tool, as tool output marked untrusted; nothing else in ContentWorker's own AI (generation, the
agents, the assistant's system prompt) uses them yet.

**Connecting a client.** With `OAUTH_ISSUER` set, the server is installable as a connector in
Claude, ChatGPT and MCP-capable IDEs: an unauthenticated request answers with
`WWW-Authenticate: Bearer resource_metadata="…"` (RFC 9728), the client fetches
`/.well-known/oauth-protected-resource`, registers itself dynamically, and runs an
authorization-code + PKCE flow that a human approves on the admin origin after signing in to the
web app, choosing the space the connection works in (a fleet deployment's issuer and resource are
`https://<domain>` and `https://<domain>/mcp`). CLI clients that cannot open a browser use
the device flow, and CI uses a personal access token. Whatever the route, the resulting token is
an ordinary API key — so an agent can still never exceed the scopes the approving human holds.
See [Auth & RBAC](./auth-and-rbac.md#oauth-21-for-mcp-clients).

order). Each calls `authorize` before delegating to the same use-case as the HTTP route. Every
tool that changes nothing carries `readOnlyHint: true`, which is also what keeps it out of the

Gaps against the HTTP API: plugin install, install-from-URL and delete are HTTP-only
([Plugins](./plugins.md)), and so is minting a personal access token: it is the one credential a
person mints for themselves, and the route refuses any caller holding an OAuth `clientId`, so a
token that expires in an hour can't issue itself one that never does
([Auth & RBAC](./auth-and-rbac.md#one-token-model-three-issuances)). API keys are on MCP like
every other `space:admin` operation (`packages/http/src/mcp/tools/api-keys.ts`, on the routes'
use-cases and body schemas). The same rule holds for them in the use-cases, on both surfaces: a
delegated bearer (an OAuth access token, or a personal access token) can't mint an operator key or
widen one's role (`assertMayMintKeys` in `packages/application/src/auth.ts`, `assignApiKeyRole` in
`team.ts`); a signed-in person, an operator key and the admin token can. (An OAuth grant never
carries `space:admin` anyway, `maxClientScopes` in `oauth.ts`.) Nor can one give a person lasting
access: `role_preset_assign` for a person, `role_update` widening a role someone holds, and
`invite_create` / `invite_resend` refuse it in the use-cases (`DelegatedPeopleError`; see
[Auth & RBAC](./auth-and-rbac.md#one-token-model-three-issuances)).

The webhook tools scope a hook the way the routes do
([Events & webhooks](./events-and-webhooks.md#webhooks)): to the `environment` argument, or
space-wide with `allEnvironments: true`.

`environment_clone` returns `{ job, createJobId, publishJobId }` and runs in the engine as bulk
jobs; `environment_delete` is irreversible, refuses `main` and any environment an alias points at,
and needs `confirm` to repeat the environment id ([Backup & restore](./backup-and-restore.md)).

The workflow tools declare the full set of MCP tool annotations (`readOnlyHint` on reads, validate
and the copilot; `destructiveHint` on `workflow_run_cancel`; `idempotentHint` where a repeat changes
nothing), and run the same use-cases and scope checks as the `…/workflows`, `…/workflow-runs` and
`…/workflow-tasks` routes.

## Skills

The server also publishes **agent skills** through the MCP Skills extension (SEP-2640,
`io.modelcontextprotocol/skills`). A skill is a `SKILL.md` describing a task end to end: which
tools to call, in what order, and which rules trip agents up. Clients that support the extension
list skills with `skills/list` and read them as `skill://contentworker/<name>/SKILL.md` resources.

| Skill                | Covers                                                                                   |
| -------------------- | ---------------------------------------------------------------------------------------- |
| `model-content`      | Creating and publishing content types, choosing field types, `model_typescript`          |
| `author-and-publish` | Finding and editing entries, versions, releases, scheduling, workflow runs and approvals |
| `import-content`     | Field mapping, `identityField`, analyze → execute, publishing the result                 |

The sources live in `packages/http/skills/<name>/`. An edge worker has no filesystem, so the files
are embedded into `packages/http/src/mcp/skills.generated.ts`, the same approach as the docs. The embed
is gitignored: `pnpm install` and turbo's `generate` task (before every check-types, test, build
and dev) rebuild it from the skill files. The catalog is loaded with `strict: true`, so a malformed skill fails loudly instead
of being skipped. If loading fails, the error is logged and the tools are served without skills;
the load is retried on the next request. It is digested once per isolate and then attached to
each request's server. Like the `docs_*` tools, skills describe the product rather than any
tenant's content, so being authenticated is the only gate.

Because the tools are thin wrappers over the use-cases, the MCP surface inherits all validation,
referential integrity, RBAC, and event emission for free.

The admin's assistant calls a subset of these tools in-process as the signed-in person; see
[Coworker](./ai-agents-and-search.md#coworker-the-admins-assistant).
