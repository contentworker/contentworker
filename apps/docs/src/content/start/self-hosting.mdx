---
title: Self-hosting
description: Install ContentWorker in your own Cloudflare account, create the first admin, upgrade it and recover it.
---

ContentWorker runs as one install in your own Cloudflare account: a database, an object storage
bucket, a key-value namespace, a vector index, queues, an AI gateway and five workers. Two scripts
manage it, and your settings live in one file.

## Before you start

- A Cloudflare account on the Workers Paid plan, and a zone in it for the install's domain.
- Node 24 and pnpm.

## Install

```sh
git clone <your clone of the repository> contentworker && cd contentworker
pnpm install
pnpm --filter @contentworker/engine exec wrangler login
cp .env.example .env     # set DOMAIN
pnpm contentworker:setup
pnpm contentworker:deploy
```

1. **Settings.** `.env` holds the install's settings as flat variables. `DOMAIN` is required: the
   admin is served at `DOMAIN`, the API at `api.DOMAIN`, the Delivery API at `cdn.DOMAIN` and
   published media at `media.DOMAIN`. A variable already in the environment wins over the file,
   and an empty one counts as unset. `.env` is gitignored.
2. **`pnpm contentworker:setup`** creates the database (with read replication), key-value namespace, object
   storage bucket, vector index, queues and AI gateway, and generates the install's secrets into
   `.secrets/secrets.env`. It is safe to re-run: what exists is kept. It never prints a secret.
3. **Back up `.secrets/`.** It is the only copy of the keys that seal stored secrets and hash API
   keys and passwords. Losing them makes what they protect unreadable, and they can't be
   regenerated. Copy the folder to a password manager or an encrypted store.
4. **`pnpm contentworker:deploy`** records a database restore point, migrates the database, deploys the
   workers (engine, media, api, delivery, web), smoke-tests the install and rolls back on a
   failure. It uses your `wrangler login`, or `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.
5. **Create the first admin.** Open `https://DOMAIN/setup` and enter `SETUP_TOKEN` from
   `.secrets/secrets.env`. Setup then walks you through your first space; see
   [Getting started](/start/getting-started/).

## Settings

| Setting                                             | What it does                                                                                                  |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `DOMAIN`                                            | Required. The admin's host                                                                                    |
| `DATA_JURISDICTION`                                 | `eu` or `fedramp`: keep the database, media bucket and Durable Objects there. Set before the first setup      |
| `AI_MAX_TIER`                                       | `flagship`, `balanced` or `fast`: the most capable model tier the install runs. Unset: no cap                 |
| `AI_GATEWAY_LOGS`                                   | Whether the AI gateway keeps a log of each model call (never prompts or answers)                              |
| `AI_MODE`                                           | `mock` runs without Workers AI, for evaluating without AI costs                                               |
| `DEMO_STARTERS`                                     | Offer the enterprise sample starter when a space is created                                                   |
| `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_TRUST_EMAIL` | Admin single sign-on with your OIDC provider; its client secret is the secret `OIDC_CLIENT_SECRET`            |
| `EMAIL_FROM`, `EMAIL_FROM_NAME`                     | Send mail (notifications, invitations, password reset codes) with Email Sending from a domain onboarded to it |
| `INSTANCE`, `RATE_LIMIT_SLOT`                       | A second install in the same account; see [Two installs](#two-installs-in-one-account)                        |

Change a setting, then run `pnpm contentworker:setup` (when it adds a resource) and `pnpm contentworker:deploy` again.

## Upgrade

```sh
git pull
pnpm install
pnpm contentworker:deploy
```

Migrations run before the new code ships and are expand-only, so the running version keeps working
while a deploy is in progress. Run `pnpm contentworker:setup` first when a release adds a resource.

## Recover access

When no administrator can sign in, run `pnpm contentworker:setup-code`. It writes a new one-time setup code to
`.secrets/secrets.env` and sets it on the web worker. Open `https://DOMAIN/setup` with it to create
one more admin account; its use is recorded in the audit log.

## Roll back and restore

A failed deploy rolls the workers back itself, engine first. To go back later, check out the earlier
commit and deploy it again. Code rolls back; the database schema does not. To restore data, use the
database's point-in-time recovery to the bookmark the deploy printed.

## Deploy on merge

For a fork that wants a push to `main` to deploy, the repository includes an optional workflow. It
does nothing until the repository variable `DEPLOY_ON_MERGE` is `true`. It then runs after CI
passes on `main`, with your settings as repository variables, your secrets on a `production`
environment limited to `main` (`pnpm contentworker:setup --github` sets the generated ones), and a
Cloudflare API token and account id.

## Two installs in one account

A second install, such as a staging copy, needs its own settings file (say `.env.staging`) with its
own `DOMAIN`, an `INSTANCE` name appended to every resource, and a `RATE_LIMIT_SLOT` from 2 to 999
that no other install in the account uses:

```sh
pnpm contentworker:setup --env-file .env.staging
pnpm contentworker:deploy --env-file .env.staging
```

Its secrets go to `.secrets/secrets-<instance>.env`: back that file up too.
