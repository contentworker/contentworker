---
title: Migrate a website
description: Bring a published website in as structured content. Read it from its sitemap or a crawl, group its pages into templates, turn each template into a content type with an import script, then load, redirect and publish the pages, over the API, MCP, the SDK and the command line.
---

A migration run reads a published website and brings its pages in as structured content. You
point a run at a site, it lists the pages, fetches them a batch at a time and groups the pages that
share a structure into **templates**: a home page, a product page, an article. Each template then
becomes a content type, and an **import script** turns each of its pages into that type's fields
and blocks. Rich text arrives as `RichTextDocument` trees, images as assets and links between
pages as links between entries; no page is stored as HTML. The run lives in one
[environment](/guides/environments/), so you can do it in a scratch environment and look at the
result before anything reaches your main content.

## What exists now

The whole run is built, on every surface:

- Management API routes under `/spaces/{space}/environments/{env}/migrations/runs` (the "Site
  migration" tag in the [API reference](/reference/rest-api/)).
- 21 [MCP](/guides/mcp/) tools, `migration_*`, and four skills: `site-migration` walks an agent
  through a run, `template-content-model` and `template-import-script` through authoring a
  template, and `migration-triage` through scores and failures.
- `cma.migrations` in the [Management SDK](/guides/sdks/) and `contentworker migrate` in the
  [command-line tool](/guides/cli/).
- **Migrations** in the admin (under Build, for roles that hold `migration:run` or
  `content:manage`): the environment's runs, a form to start one, and each run's steps, templates
  and pages. **Fetch until done** keeps fetching batches until no pages are waiting, and can be
  stopped at any point. A template's page is where it is reviewed: its content model and import
  script to read or edit, **Try on sample pages** with what each page would become, **Approve**,
  then **Transform** and **Load**. The run's page ends with **Relink**, **Redirects**, **Publish**
  and **Run in the background**.

A small site can be taken through step by step, each call a bounded batch. A large one is handed to
the engine with `start`, which runs every step in the background and waits for people only where
a person decides: approving each template, and the go-ahead to publish.

## Before you start

Each step needs `migration:run`, and the steps that write content need what that write needs too:

| Step                                                  | Needs                                                        |
| ----------------------------------------------------- | ------------------------------------------------------------ |
| Create, inventory, fetch, cluster                     | `migration:run`                                              |
| Read a run, its pages and templates, a script         | `migration:run` or `content:manage`                          |
| Propose a model, write or try a script, transform     | `migration:run`                                              |
| Approve a template                                    | `content:manage`                                             |
| Load pages as entries                                 | `migration:run`, `content:write` and `assets:write`          |
| Relink                                                | `migration:run` and `content:write`                          |
| Redirect old URLs                                     | `content:manage`                                             |
| Publish, or give a started run the go-ahead to        | `content:publish` (and `content:write` through a release)    |
| Start a run in the background                         | `migration:run`                                              |

- `space:admin` carries `migration:run`, so the Administrator role and every admin key can run a
  migration. Other roles and keys can be given the scope on its own; the token picker calls it
  **Migrate websites**. See [API keys and access](/guides/api-keys/#scopes).
- A connected app (OAuth, which includes `contentworker login` and MCP clients) can ask for
  `migration:run`; its token carries it only when the approving person's role does.
- Whatever a step writes, it writes as whoever called it: entries, assets and redirects are
  stamped with the caller, and a run started in the background acts for the person who started it
  and the people who approve. No request names someone else.
- The site must be public: a run has no way to sign in to it.

## How the site is read

| Rule                | Behavior                                                                                                                                           |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Same origin         | Every request stays on the origin of the source URL. Links to other hosts are counted and never followed.                                          |
| `robots.txt`        | Read as the user agent token `ContentWorker`. Pages it disallows are left out and counted. A crawl delay it asks for is honoured, up to 10 seconds. |
| Unreadable `robots.txt` | A server error or no answer means nothing is fetched or written: an inventory answers `503`, a fetch answers with `unavailable`. A `4xx` answer means no rules.                |
| Public addresses    | A source URL on a loopback, link-local or private address is refused when the run is created (`422`, naming `source.url`).                         |
| Page URLs           | The query string and fragment are dropped, so `/shop?page=2#top` is the page `/shop`.                                                              |
| Stored HTML         | Each page's HTML is kept in object storage, addressed by its hash. It is never returned: a page reports `{ sha256, bytes }` only.                  |

## Choose a source

A source is a `kind`, a `url` and optional limits.

| Field      | Meaning                                                                                                                                              |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kind`     | `sitemap` or `crawl`                                                                                                                                 |
| `url`      | For `sitemap`, a sitemap URL, a sitemap index, or the site's origin (its `robots.txt` `Sitemap` lines are read, then `/sitemap.xml`). For `crawl`, the start page. |
| `include`  | Path globs; a page must match one. Empty means every page.                                                                                           |
| `exclude`  | Path globs that leave a page out, over `include`.                                                                                                    |
| `maxPages` | The most pages the run takes. Default 500, at most 10,000.                                                                                           |

A glob starts with `/`. `*` matches within one path segment and `**` across segments, so `/blog/*`
takes `/blog/hello` but not `/blog/2024/hello`, and `/blog/**` takes both. Prefer a sitemap: it
lists the pages directly. A crawl starts at one page and follows its links up to eight levels
deep, adding the pages the globs take as it goes, so it needs more fetches and can miss pages
nothing links to.

## Run it

1. **Create** the run. Nothing is fetched yet. `name` defaults to the source host, and `threshold`
   (0 to 1, default 0.8) is the score a page will need later to count as validated.
2. **Inventory** it. A sitemap source adds every listed page the globs take, up to `maxPages`; a
   crawl adds its start page. The run's `inventory` says how many pages were found and added, how
   many were skipped (by `robots.txt`, globs, origin, `maxPages` or an unusable URL) and any
   warnings. Repeating it adds only URLs the run doesn't hold, and it is refused (`400`,
   `invalid_state`) once the run is clustered.
3. **Fetch** in batches. Each call fetches up to `limit` pages (1 to 10, default 10) that haven't
   been fetched, and answers `{ fetched, failed, added, more }`. Call again while `more` is
   `true`. A crawl's `added` counts the links it found on the batch's pages. A page that fails
   (a `404`, a timeout) keeps its `error` and isn't tried again. When the site can't be read,
   the answer carries `unavailable`, nothing was written, and you call again later with the same
   arguments.
4. **Cluster.** Pages that share an HTML structure become one template. `threshold` (0 to 1,
   default 0.6) is how similar a page must be to join one: lower it if one page shape was split
   into several templates, raise it if unlike pages were merged. Clustering again replaces the
   earlier grouping whole, until a template is being authored or a
   [background run](#run-it-in-the-background) has taken the templates on.
5. **Read the result.** The run shows its page counts by stage and its templates, largest first,
   each with sample pages. List a run's pages by `stage` or `template`; a one-page template is
   usually a one-off such as a home page.

`status` on a run is the step that last finished: `created`, `inventoried`, `clustered` or
`failed`.

## Author each template

Work one template at a time, largest first. A template's `status` goes `pending` → `authoring`
(once a model or script is written; clustering again is refused from then on) → `approving` (while
an approval writes its content type) → `approved`, and back to `authoring` if it is reopened.

1. **Propose its model**: the content type its pages become. The server checks it as the type will
   be created and refuses one without:
   - exactly one top-level blocks field (an `Array` of `Component` variants) for the body, one
     variant per kind of section;
   - a URL pattern, such as `/blog/{slug}`, so each old path can redirect to its entry;
   - a `sourceUrl` field (`Symbol`, unique, not localized) that holds each entry's source page URL.
     Leave it out and it is added. A load matches entries on it, which makes loading safe to
     repeat.

   A preview URL, agent instructions, the editor layout and each field's help text and defaults
   are dropped: the person who approves adds them. Proposing changes nothing in your model.
2. **Write its import script**, an ES module of at most 256 KiB, sent and read back as text. Its
   default export takes the parsed page and returns
   `{ fields, blocks: [{ variant, fields }], assets: [{ url, alt? }], links: [{ href }] }`. A
   rich-text value is `{ "$html": "<p>…</p>" }`, the fragment as the page holds it; an asset link
   is `{ "$asset": "https://…/a.png" }`. Scripts run in an isolate of their own with no network.
3. **Try it** on the template's sample pages, or up to five pages you pick. Each result says
   whether the output fits the model, its score against the page (text coverage, lost links,
   missing images) and the script's logs; outputs come back with every `$html` already converted
   to a rich-text document. The summary is kept as the template's `lastTry`.
4. **Approve it.** A person with `content:manage` reads the template, including its
   `reviewDigest`, and approves with that digest as `reviewed`. Approval creates and publishes the
   content type, as them. If the model or script changed after they read it, approval answers
   `409` and they review again. An approved template's model and script are held until it is reopened. In the admin,
   the approval sends the digest of the version on screen; when the template changes meanwhile, the
   page shows the new version and asks for it to be read before it can be approved.

## Change an approved template

When a template's pages need another script or model after all, a person with `content:manage`
reopens it: **Reopen for changes** in the admin, `contentworker migrate reopen`, or `reopen` with
the `reviewDigest` they read. It goes back to `authoring`, and is proposed, scripted, tried and
approved again as before.

- It keeps its content type, so the model's `apiId` can't change: a proposal with another one is
  refused (`422`). Approving again saves the type as the proposal says, through the type's own
  checks: removing a field that holds content is refused. What someone changed on the type by hand
  since, such as field help, is replaced.
- Pages that aren't loaded yet are transformed again by the new version. Until they are, a load
  leaves them and counts them as `stale`. A version is the model and the script together, so a
  change to either counts; approving it again unchanged takes no page again.
- Pages already loaded or published, and their entries, are left as they are, with the edits people
  made to them. The template's `pageVersions` counts the ones an earlier version made.
- A transform or load that is running when the template is reopened stops with `409`, and moves no
  page. An entry that load had already written stays, and is updated when its page is loaded.
- A background run waits for the new approval, 14 days at a time and for up to 8 approvals of a
  template, and takes the new version through. An approval given after the go-ahead to publish is
  taken on step by step. The authoring agent isn't started again, and stops when the template is
  first approved: a person (or an agent on the API) changes it from there.

## Take the pages in

Step by step, each call a bounded batch:

1. **Transform** up to 10 pages a call (`limit`, `after` from the last call's `next`, while
   `more`). Each page is scored and moves to `validated` at the run's threshold or `needs-fix`
   below it. Pages already transformed by the approved version are skipped, and so are
   loaded and published ones.
2. **Load** up to 10 `validated` pages a call as entries, while `more`. The assets each output
   names are downloaded once per run; a file that fails is reported and its page loads without it.
   `includeNeedsFix` loads the low scorers too, but not a page with an error: reopen the template
   and fix its script or model, or bring those in by hand. Loading a page again updates the entry it became.
3. **Relink** once every template is loaded, with `after` until `next` is absent: links between
   migrated pages become links between their entries.
4. **Redirect**: a 301 from each loaded page's old path to its entry's path, by the type's URL
   pattern. Pages whose path didn't move are skipped. Safe to repeat.
5. **Publish** up to 50 loaded entries a call, or with `viaRelease` add them to a release
   (`releaseId`, or the run's own, titled `releaseTitle`) for someone to ship, again with `after`
   until `next` is absent. Naming a release without `viaRelease` is refused (`422`). Publishing is
   public and the run doesn't undo it, so the admin asks first, with the number of entries.

## Run it in the background

`start` hands the run to the engine, acting for you: it inventories, fetches and clusters, starts
an authoring agent for each of the largest templates, then for each template a person approves
transforms, loads and redirects its pages, relinks, and waits for the go-ahead to publish
(`publish-approval`), which names its approver from the caller's credentials and is recorded on
the run. Starting again is
safe: it answers `started: false`. Approving a template tells the engine (`signalled: true`);
otherwise `reason` says why: `no-driver` (the run is taken step by step), `driver-finished`, or
`unreachable`, when approving again tells it. A go-ahead for a run that was never started answers
`404`.

A run takes one go-ahead, and it stands. Giving the same one again as the same caller is safe, after a
lost answer say; anyone else's, or one for another target, is refused (`409`, `details.reason`
`go_ahead_taken`). With `signalled: false` it was recorded but the engine couldn't be reached: send
the same one again. One that never arrives is still taken when the 14-day wait ends.

Reading the run says where its background run is: `driver.state` is `none`, `running`, `waiting`,
`paused`, `finished`, or `unknown` while the engine can't be asked. `driver.startedBy` and `startedAt`
say who started it, and `driver.goAhead` whether one was `given`, by whom, when, for what, and whether
it certainly arrived (`delivered`). Runs started before this was recorded read `unknown` there. The
admin shows the same on the run's page, under **Run in the background**.

A template reopened while the run
is driven is waited for again, and doesn't hold up the others. The go-ahead publishes every entry
loaded by then, a reopened template's too; its pages not loaded yet aren't published, and are taken
on step by step once it is approved again. If no template is approved in time, or the go-ahead never comes, the engine stops waiting
and the run's status becomes `stopped`. A stopped run, a failed one, or one whose engine run has
finished can't be started or given the go-ahead again (`400`), but its templates can still be
approved, loaded and published step by step. From the moment the engine takes a run's templates on,
the run carries `clusteringHeldAt` and its pages can't be clustered again (`400`, `invalid_state`),
whatever becomes of the engine run. Until then you can cluster it by hand as often as you need; fetch
every page first, because a page fetched after the clustering the engine takes joins no template. To
group the pages another way afterwards, create another run. Follow the run with its status and pages as before.

### With curl

```sh
BASE="$API/spaces/$SPACE/environments/main/migrations/runs"
AUTH="Authorization: Bearer $TOKEN"

RUN=$(curl -s -X POST "$BASE" -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"source":{"kind":"sitemap","url":"https://example.com","exclude":["/blog/**"],"maxPages":2000}}' \
  | jq -r .id)

curl -s -X POST "$BASE/$RUN/inventory" -H "$AUTH"

# Fetch until no page waits.
while [ "$(curl -s -X POST "$BASE/$RUN/fetch" -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"limit":10}' | tee /dev/stderr | jq -r '.more and (.unavailable | not)')" = true ]; do :; done

curl -s -X POST "$BASE/$RUN/cluster" -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"threshold":0.6}'
curl -s "$BASE/$RUN/templates" -H "$AUTH"
curl -s "$BASE/$RUN/pages?stage=clustered&limit=50" -H "$AUTH"
```

A page list returns `nextCursor` only while more pages follow; send it back as `cursor`.

Then each template, then the pages:

```sh
T="$BASE/$RUN/templates/$TEMPLATE"
curl -s -X POST "$T/proposal" -H "$AUTH" -H "Content-Type: application/json" -d @model.json
jq -Rs '{script: .}' import.js | curl -s -X PUT "$T/script" -H "$AUTH" \
  -H "Content-Type: application/json" -d @-
curl -s -X POST "$T/try" -H "$AUTH" -H "Content-Type: application/json" -d '{}'

# A content manager reads the template, then approves what they read.
DIGEST=$(curl -s "$T" -H "Authorization: Bearer $MANAGER" | jq -r .reviewDigest)
curl -s -X POST "$T/approve" -H "Authorization: Bearer $MANAGER" \
  -H "Content-Type: application/json" -d "{\"reviewed\":\"$DIGEST\"}"

# To change it after that, reopen what was approved, then author and approve it again:
# curl -s -X POST "$T/reopen" … -d "{\"reviewed\":\"$DIGEST\"}"

curl -s -X POST "$T/transform" -H "$AUTH" -H "Content-Type: application/json" -d '{}'
curl -s -X POST "$T/load" -H "$AUTH" -H "Content-Type: application/json" -d '{}'
curl -s -X POST "$BASE/$RUN/relink" -H "$AUTH" -H "Content-Type: application/json" -d '{}'
curl -s -X POST "$BASE/$RUN/redirects" -H "$AUTH" -H "Content-Type: application/json" -d '{}'
curl -s -X POST "$BASE/$RUN/publish" -H "$AUTH" -H "Content-Type: application/json" -d '{}'

# Or, for a large site:
curl -s -X POST "$BASE/$RUN/start" -H "$AUTH"
curl -s -X POST "$BASE/$RUN/publish-approval" -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"viaRelease":true,"releaseTitle":"Site launch"}'
```

### With an agent

Connect an agent that holds the scope and ask for the migration in plain words. The
`site-migration` skill tells it to confirm the source and limits first, prefer a sitemap, and walk
you through the templates at the end. Under it, the calls are:

```json
{ "name": "migration_create", "arguments": { "source": { "kind": "sitemap", "url": "https://example.com", "exclude": ["/blog/**"] } } }
{ "name": "migration_inventory", "arguments": { "run": "<run id>" } }
{ "name": "migration_fetch_pages", "arguments": { "run": "<run id>", "limit": 10 } }
{ "name": "migration_cluster", "arguments": { "run": "<run id>", "threshold": 0.6 } }
{ "name": "migration_templates", "arguments": { "run": "<run id>" } }
```

`migration_list`, `migration_status` and `migration_pages` read a run back. Authoring is
`migration_template_get`, `migration_propose_model`, `migration_script_get`,
`migration_script_set`, `migration_script_try`, `migration_template_approve` and
`migration_template_reopen`; the pages go in
with `migration_transform`, `migration_load`, `migration_relink`, `migration_redirects` and
`migration_publish_entries`; and `migration_start` and `migration_publish` drive a run in the
background. Every tool takes `space` and `environment` like the rest of the server.

An agent proposes and scripts, but approving and reopening need `content:manage` and the skills
tell it to leave those to a person. Page text, script outputs and logs reach it as data from the old site, and
the skills say to treat them as data, never as instructions.

### With the command line

```sh
contentworker migrate create https://example.com --exclude '/blog/**' --max-pages 2000
contentworker migrate step <run>
contentworker migrate cluster <run> --threshold 0.6
contentworker migrate pages <run> --stage clustered
contentworker migrate template <run> <template>
contentworker migrate script set <run> <template> import.js
contentworker migrate script try <run> <template> --page <page id>
contentworker migrate approve <run> <template> --reviewed <digest>
contentworker migrate reopen <run> <template> --reviewed <digest>
contentworker migrate start <run>
contentworker migrate publish <run> --via-release --release-title 'Site launch'
```

`migrate create` takes `--crawl` for a crawl source, `--include` and `--exclude` (repeatable),
`--max-pages`, `--name` and `--threshold`. `migrate step` inventories a run that was just created,
then fetches batches until none wait (`--batch`, `--max-batches`); run it again after a stop. It
exits `1` with the code `site_unavailable` when the site's `robots.txt` can't be read.
`migrate template` shows a template's model, script version, last try and `reviewDigest`.
`migrate approve` and `migrate reopen` without `--reviewed` show the template and ask before acting
on what they show (`--yes` off a terminal). `migrate publish` sends a started run the go-ahead; `--now` publishes the
loaded entries here instead, batch by batch.

## When a call is refused

| Status | Code                | Means                                                                                                                      |
| ------ | ------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `403`  | `forbidden`         | The token lacks the scope; the message names it.                                                                           |
| `400`  | `invalid_state`     | The step is out of order: clustering before an inventory, once a template is authored or once a background run has taken the templates on, a script change once a template is approved, a transform or load before approval, or a start or go-ahead for a run that failed, stopped or whose engine run has finished. |
| `404`  | `not_found`         | No such run or template in this environment, or no background driver to send a go-ahead to.                                |
| `409`  | `conflict`          | Another step wrote the run first (`retryable: true`; send the call again), or a go-ahead to publish was already given (`go_ahead_taken`; it stands), or the template changed since its `reviewDigest` was read (review it again), or it was reopened while its pages were transformed or loaded. |
| `422`  | `validation_failed` | A source field is malformed, or the URL is on a private address. The issue names the field, such as `source.include[0]`. |
| `501`  | `not_configured`    | This deployment can't read source sites, run import scripts, or run migrations in the background.                         |
| `503`  | `site_unavailable`  | The site's `robots.txt` can't be read (`retryable: true`). Nothing was written; try again later.                            |
