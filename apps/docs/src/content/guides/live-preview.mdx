title: Live preview
description: Let the admin frame your frontend and re-render each unsaved edit in it, from the entry editor's Site view and the page side of the live preview channel.
---

Live preview shows an editor their edits on your real site before they save. The admin frames
your frontend, sends it the entry being edited and then each edit as a patch; your page applies the
patch to its copy of the fields and re-renders. The admin draws selection, hover and the seams
between blocks itself, outside the frame, from where your page says things are. Nothing unsaved
reaches the API from your page.

## In the editor

Give the content type a [preview URL](/guides/content-modeling/#preview-url), and the entry
editor's side pane gains a **Site** view beside Details and Preview. It shows the entry's page on
your site, framed, and re-renders it as the editor types; saving works exactly as it does without
it. A type with no preview URL has no Site view.

- **Edit** and **View**: in edit mode a click on a marked element selects it and focuses that field
  (or that block, in its blocks field) in the form, and your page's links go nowhere. In view mode
  your page behaves as it does on its own, links and all.
- **Desktop**, **Tablet** and **Phone** render your page at 1280, 768 or 390 pixels wide, scaled
  down to fit the pane, so a layout never depends on how wide the editor's window is.
- In edit mode, undo, redo and the other forwarded keys pressed in your page act in the editor;
  Escape clears the selection.

The page the admin frames is your preview URL, filled for the entry with a preview token that lasts
an hour, plus a `cw_session` parameter minted fresh for each load. Your page must allow the admin
to frame it: if it sends `Content-Security-Policy: frame-ancestors` or `X-Frame-Options`, name the
admin's origin (`frame-ancestors https://your-workspace.contentworker.app`). The admin frames it
sandboxed (scripts, forms and its own origin; no popups, downloads or navigating the editor's
window) and sends no `Referer`.

If your page loads but never answers, the pane says it doesn't speak live preview yet and shows it
as saved. If it navigates elsewhere (a link followed in view mode), the pane offers the way back
to the entry's page. If it answers from another origin than the preview URL names (a redirect to
`www.`, say), the pane says so: set the preview URL to the address the page is served from.

## Start it

```ts
import { startLivePreview } from '@contentworker/sdk/live-preview';

const preview = startLivePreview({
  adminOrigin: 'https://your-workspace.contentworker.app',
  onChange: async (fields, update) => {
    // Re-render with `fields`: the whole page, or just the blocks `update.ops` touched.
    await render(fields);
  },
});

// Later, on teardown:
preview.destroy();
```

It does nothing (and `preview.active` is `false`) unless the page is in a frame and its URL carries
a `cw_session` parameter, so the same build ships to production. Your page keeps its own scrolling
in the frame: sticky headers, full-height heroes and lazy loading behave as on the live site.

| Option        | Meaning                                                                                                  |
| ------------- | -------------------------------------------------------------------------------------------------------- |
| `adminOrigin` | Required. The admin's exact origin (https; http only on `localhost`). Messages from any other origin are ignored; the page posts only to it. |
| `onChange`    | Called with the edited fields once the entry arrives, then after each patch. May return a promise.       |
| `onSelect`    | The editor selected a block or field in the admin (`{ key }` or `{ ref }`), or cleared it.               |
| `onHover`     | The editor's pointer is over a block or field in the admin's outline, or none.                          |
| `newKey`      | Mints a `_key` for a block a patch brings without one. Default: a random UUID.                           |

`fields` is locale-keyed, as the Management API returns an entry (`{ title: { 'en-US': 'Home' } }`).
`update` says which entry and locale (`entryId`, `contentType`, `locale`, `version`), the last
patch included (`seq`) and the ops since the last call (`ops`). Empty `ops` means the whole entry
arrived (the first time, and whenever the admin sends it again): render everything, not only what
changed. Patches that arrive while `onChange` is still running are folded into the next call, so a
slow render never queues up a backlog. The admin hears an edit is on screen when the promise
`onChange` returns settles. If it throws, the admin is told the render failed and nothing in that
call counts as rendered; its ops come again in the next call, made when the next edit arrives.

In React, `useLivePreview` does the same for as long as the component is mounted, and returns the
fields to render:

```tsx
import { useLivePreview } from '@contentworker/sdk/react';

function Landing({ entry }) {
  const live = useLivePreview({ adminOrigin: 'https://your-workspace.contentworker.app' });
  const fields = live.fields ?? entry.fields;
  // …render from fields
}
```

It returns `{ active, fields, update }`; `fields` is `undefined` until the admin sends the entry,
and always outside a session.

## Mark up your page

The admin finds things on your page by three attributes:

| Attribute       | On                                              | Holds                                                    |
| --------------- | ----------------------------------------------- | -------------------------------------------------------- |
| `data-cw-block` | A block's root element                          | The block's `_key`                                       |
| `data-cw-slot`  | The element directly holding a list of blocks   | The blocks field's apiId, or the slot's apiId on its block |
| `data-cw-ref`   | An element rendering one field                  | The field's ref, as [inline editing](/guides/sdks/#inline-editing) marks it |

```tsx
import { blockAttrs, slotAttrs } from '@contentworker/sdk/live-preview';

<main {...slotAttrs('body')}>
  {body.map((block) => (
    <section key={block._key} {...blockAttrs(block._key)}>
      <h2>{block.title}</h2>
      <div {...slotAttrs('items')}>{/* the section's own blocks */}</div>
    </section>
  ))}
</main>
```

A slot inside a block belongs to the nearest `data-cw-block` around it.

## Edit and view modes

The admin switches the page between two modes. In view mode, your page behaves exactly as it does
on its own. In edit mode:

- A click on a marked element selects it in the admin instead of reaching your page's handlers. A
  field's ref wins over the block it sits in.
- A click on a link outside any marked element, or a ⌘-click or Ctrl-click on any link, asks the
  admin to navigate the frame; the page never follows a link itself.
- Hovering reports the marked element under the pointer, at most once a frame.
- Undo (⌘Z or Ctrl+Z), redo (with Shift), Escape, `/`, Delete, Backspace and the arrow keys go to
  the admin, except while typing in a form field. Other keys stay with your page.

## The protocol

Every message is an object `{ cw: 1, session, type, … }`, where `session` is the `cw_session`
value; anything else is ignored. The page accepts a message only from the admin origin, from its
parent window, for its own session, and never evaluates anything in one. The session tells one
framing from another; it isn't a secret, since it is in the page's URL. Each side checks the
other's origin and window before reading a message.

Unsaved edits are rendered into your page, so any script your page runs (analytics, tag managers,
third-party widgets) can read them while the editor works. Keep scripts you wouldn't trust with
drafts off your preview deployment.

| From admin | Carries                                                       |
| ---------- | ------------------------------------------------------------- |
| `init`     | `fields`, `locale`, `version`, `entryId`, `contentType`, and optionally `seq`, the last patch they include (0 when absent) |
| `patch`    | `seq` (only goes up; a patch at or below the last is ignored) and `ops` |
| `select`   | `key` or `ref`, or neither to clear                           |
| `hover`    | `key` or `ref`, or neither                                    |
| `scrollTo` | `key` or `ref`                                                |
| `mode`     | `edit` or `view`                                              |

| From page  | Carries                                                       |
| ---------- | ------------------------------------------------------------- |
| `hello`    | `sdkVersion`, `capabilities`                                  |
| `rendered` | `seq`: everything up to it is on screen                       |
| `geometry` | `blocks`, `slots` with their `gaps`, `fields`, `scroll`, `viewport`, `docHeight`, and `truncated: true` when some boxes were left out |
| `pick`     | `key` or `ref`                                                |
| `hover`    | `key` or `ref`, or neither                                    |
| `navigate` | `url`: https (http only on `localhost`), on your site's origin |
| `key`      | `key`, `meta`, `ctrl`, `shift`, `alt`                         |
| `error`    | `kind` (`invalid`, `patch`, `render` or `target`), `message`, and for `patch` and `render` the `seq` it concerns |

A patch's ops are those of the Management API's block patch (`insert`, `update`, `move`, `remove`,
`duplicate`, addressed by `_key` with a `field` and `locale`), plus `setField { field, locale,
value }` for an ordinary field. Send them in the form the block patch answers with (`applied`),
every key present: a key the page mints for a block sent without one is the page's own.

A patch applies whole or not at all. When one can't apply, or arrives too large or malformed to
read, the page keeps the fields it had and answers `error` with kind `patch` and that patch's
`seq`. From then on it is out of step: it drops every later patch, answering the same error again,
until the admin sends `init`, which resets it. If the same patch is refused again after that, the
admin sends the fields it changed whole, as `setField`, which always applies.

Geometry is in the frame's viewport, in CSS pixels, and is sent when something moves (a resize, a
scroll, a change to the page), at most once a frame and only when it changed. Each slot lists its
gaps: the place before its first block, between each pair and after its last, with the insertion
`index` and the blocks on either side. A page with more boxes than one message holds sends those
on screen first, then those nearest it, and marks the message `truncated`.

Limits: a message is at most 256 KB (an `init`, which carries the whole entry, 2 MB); a patch has at
most 100 ops; a geometry message reports at most 2,000 blocks, slots and fields each, and 4,000
gaps.
