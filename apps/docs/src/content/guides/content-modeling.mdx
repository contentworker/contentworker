A content model is the set of content types in a space. You define it in the admin (**Content →
New content type**) or over the API and MCP. Good models describe content by what it
*is* (an article, an author, a promo block) rather than where it appears, so the same entry can
feed a website, an app, an email and an agent.

## Content types

A content type has:

- an **`apiId`**, the stable identifier the API and SDKs use (`article`), which never changes;
- a **name** people see (`Article`);
- a **display field**, the field used as each entry's title in lists, pickers and search results;
- an ordered list of **fields**;
- optionally a **URL pattern**, where its entries live on your site;
- optionally **singleton**: it holds one entry only.
- optionally a **group**, **description** and **icon**, and an editor **layout** (see
  [Organizing the model](#organizing-the-model)).

Creating or changing a content type makes a draft definition. Each revision bumps the type's
`version`; publishing marks that version live for authoring and delivery and emits a
`content_type.published` event, so integrations (generated types, caches) can react. The admin's
content type dialog publishes as it saves.

### URL pattern

A URL pattern is a path starting with `/` that says where a type's entries live on your site, for
example `/blog/{slug}`. Its placeholders are `{id}` (the entry id), `{locale}`, or the API ID of one
of the type's own `Slug` fields; anything else is refused. In the content type dialog it is the
**URL pattern** field; over the API and MCP it is `urlPattern` on `POST …/content-types` and
`model_create_content_type` (`null` clears it). When a publish changes a slug the pattern names on
an entry that was already published, contentworker writes a `301` from the old path to the new one;
see [Redirects](/guides/redirects/#redirect-slug-changes). A revision that removes a slug a kept
pattern names is refused.

### Singletons

A singleton type holds at most one entry outside the trash: site settings, a home page, a footer.
In the content type dialog it is **One entry only (singleton)**; over the API and MCP it is
`singleton: true` on `POST …/content-types` and `model_create_content_type` (left out of a
revision, it stays as it was). A second entry is refused with `409` on every path that makes one:
create, bulk create, duplicate, import, a snapshot restore, a promotion or an environment merge.
Trashing the entry frees the place; restoring it is refused while another entry has taken it.
Turning `singleton` on is refused while the type has more than one entry outside the trash, and
names them. A promotion that would give a singleton a second entry is refused when it is
requested, before anyone approves it. Cloning an environment, or exporting and importing one,
keeps the flag.

The admin's sidebar opens a singleton's entry in the editor (or a new one when it has none)
instead of a list. Delivery serves it by the type's API ID, with no entry id:
`GET …/singletons/{apiId}` (see [Reading content](/guides/reading-content/#singletons)). Delivery
goes by the type as last published: turning `singleton` on or off takes effect there (REST and
GraphQL alike) when you publish the type. Turned off in a draft, the type can take more entries
at once; until that draft is published, Delivery serves the published entry with the lowest id.

## Field types

| Type        | Holds                                                | Value                          |
| ----------- | ---------------------------------------------------- | ------------------------------ |
| `Symbol`    | Short, single-line text: titles, names, labels       | string                         |
| `Slug`      | A URL-safe identifier, normalized as you type        | string                         |
| `Text`      | Long, multi-line plain text                          | string                         |
| `RichText`  | A structured document: headings, lists, tables, links, embeds | object                |
| `Integer`   | A whole number                                       | integer                        |
| `Number`    | A decimal number                                     | number                         |
| `Boolean`   | Yes or no                                            | boolean                        |
| `Date`      | A date, a date and time, or a time of day ([formats](#dates)) | string                 |
| `Location`  | A point on a map                                     | `{ "lat": …, "lon": … }`       |
| `Seo`       | Search title, description, canonical URL, noindex and social image ([SEO](/guides/seo/)); one per type | object |
| `JSON`      | Free-form structured data                            | object                         |
| `Link`      | A reference to an entry or an asset                  | `{ "id": …, "linkType": … }`   |
| `Component` | A group of nested fields (a "hero", a "call to action") | object                      |
| `Array`     | A list of `Symbol`, `Text`, `Integer`, `Number`, `Date`, `Link` or `Component` items | array |

Each field also says whether it is **required**, **localized** (a separate value per locale) and
**unique** (no two entries of the type may share a value; a clash is refused with the entry that
holds it). A field can carry a **default value** that new entries start with.

### Rich text

A `RichText` value is a document of nodes: paragraphs, headings, lists, quotes, code blocks, rules,
tables, links, embedded entries and assets, and external media embeds. Every write is checked
against that vocabulary, whoever makes it: an unknown node type is refused, a link must point at an
`http`, `https`, `mailto` or `tel` address (or a relative one), and a document may be at most
512 KiB and 64 levels deep.

An **embed** holds a video, a post or a track from an allowed provider: YouTube, Vimeo, X, Bluesky,
Mastodon, Spotify or SoundCloud. It is an `embed` node whose `data` is structured metadata, never the
provider's player HTML:

```json
{
  "nodeType": "embed",
  "data": {
    "url": "https://www.youtube.com/watch?v=dQw4w9WgXcQ",
    "provider": "youtube",
    "kind": "video",
    "title": "Never Gonna Give You Up",
    "authorName": "Rick Astley",
    "thumbnail": { "url": "https://i.ytimg.com/vi/dQw4w9WgXcQ/hqdefault.jpg", "width": 480, "height": 360 },
    "width": 200,
    "height": 113,
    "aspectRatio": 1.7699
  },
  "content": []
}
```

Only `url` (https) and `provider` are required. Paste a provider URL into the rich-text editor and it
becomes an embed with a preview card; the editor fills the rest by calling
`POST /spaces/<space>/environments/<env>/embeds/resolve` (the `embed_resolve` MCP tool), which asks
the provider's oEmbed endpoint and returns only these fields. A URL that isn't https or isn't on an
allowed provider is refused. Imported HTML keeps provider players, tweet blockquotes and WordPress
embed blocks as embeds, with the URL and provider only.

Your front end decides how an embed looks: a player built from `provider` and `url` (for example
`https://www.youtube-nocookie.com/embed/<id>` in an `<iframe>` sized by `aspectRatio`), or the safe
default, a link card with the thumbnail and title, which `embedCard` in `@contentworker/sdk`
builds for you. A `mastodon` embed's host is whatever instance the author named, so don't frame it
in a player unless that instance is on your own list; the link card is always safe.

### Components and repeaters

A `Component` field groups nested fields that belong together: a hero block's heading, image and
button. An `Array` of components is a **repeater**: a list of feature cards, FAQ items or table
rows that editors add, remove and reorder.

The admin's content type dialog can't author a `Component` field, because it has no way to define
the nested fields: create one with the API (`POST …/content-types`) or the
`model_create_content_type` MCP tool. Existing component fields load and edit in the dialog.

Nested fields are ordinary fields, with three exceptions. They can't be localized on their own
(localization is decided once, on the field holding the component), they can't be unique, and they
can't be slugs. Components nest up to three levels; anything deeper is usually better as its own
content type, linked.

### Blocks

A **blocks** field is a list whose items can each take a different shape: a landing page body made
of a hero, then a section of rich text, then a call to action, in whatever order the editor picks.
It is an `Array` of `Component` that lists **variants** instead of one set of fields. In the
content type dialog, pick **Blocks** as the field's type, then add a block type for each shape
(a name, an API ID and its fields). In the entry editor, **Add block** offers those types; blocks
reorder and remove like repeater items.

Over the API or MCP, declare `items.variants` in place of `items.fields`:

```json
{
  "apiId": "body", "name": "Body", "type": "Array", "localized": false, "required": false, "position": 2,
  "items": {
    "type": "Component",
    "variants": [
      { "apiId": "hero", "name": "Hero", "fields": [
        { "apiId": "heading", "name": "Heading", "type": "Symbol", "localized": false, "required": true, "position": 0 }
      ] },
      { "apiId": "cta", "name": "Call to action", "fields": [
        { "apiId": "target", "name": "Target", "type": "Link", "linkType": "Entry", "localized": false, "required": false, "position": 0 }
      ] }
    ]
  }
}
```

Each stored block names its variant in `_type` and carries a `_key` the server assigns when the
entry is saved: `{ "_type": "hero", "_key": "0192f4a1-…", "heading": "Spring launch" }`. Send
existing blocks back with their `_key` and they keep it, so a front end can use it as a stable
identity across reorders. A variant's fields follow the component rules above. For a slot that
holds at most one block, set `validations: { size: { max: 1 } }` on the field. Links inside
blocks resolve with `include` like any other, GraphQL types the field as a union with one type per
variant, and the generated TypeScript types narrow on `_type`.

### References

A `Link` field points at an entry or an asset; an `Array` of links holds several. Restrict which
content types a link may target with `linkContentTypes`. Publishing an entry checks that
everything it links to exists, and an entry other published entries link to can't be permanently
deleted until those links are removed.

## Validations

| Validation          | Applies to                 | Checks                                       |
| ------------------- | -------------------------- | -------------------------------------------- |
| `in`                | Symbol, Text, Integer, Number | The value is one of a list (bare values, or `{ value, label }`) |
| `regexp`            | Symbol, Text               | The value matches a pattern, or a named [preset](#pattern-presets) |
| `range`             | Integer, Number            | The value is between a min and a max         |
| `size`              | Symbol, Text, Array        | Length, or number of items, is within bounds |
| `linkContentTypes`  | Link, Array of Link        | The linked entry is one of these types       |
| `dateRange`         | Date                       | The date is between a min and a max          |
| `assetMimeTypes`    | Asset Link, Array of them  | The linked asset's file is one of these types (`image/*` for a family) |

Validations run on every write, from every surface: the admin, the API, imports, AI drafting and
agents. An AI agent can't save an entry a person couldn't. `assetMimeTypes` checks the file type an
asset was declared with when it was uploaded, not the file's contents.

Give `in` options labels and an entry still stores the value: editors pick by label from a select,
and relabelling an option never invalidates content. Bare values and labelled options mix in one
list; a value can't be empty, and `'1'` and `1` count as the same value. To replace a rule's
default error, add `messages`, keyed by rule (`in`, `regexp`, `range`, `size`, `dateRange`,
`assetMimeTypes`); a message for a rule
the field doesn't declare is refused, and so is one on a list's elements (`items`), whose rules
aren't enforced per element yet.

```json
{
  "apiId": "zip",
  "name": "ZIP code",
  "type": "Symbol",
  "validations": {
    "regexp": { "pattern": "^\\d{5}$" },
    "messages": { "regexp": "Enter a five-digit ZIP code" }
  }
}
```

### Pattern presets

Instead of writing a regular expression, name a preset: `email`, `url` (http or https), `slug`,
`phone` (international format, `+14155550123`), `hexColor` or `usZipCode`. Saving the type fills in
the preset's pattern beside its name, so the rule reads the same everywhere:

```json
{ "apiId": "contact", "name": "Contact email", "type": "Symbol",
  "validations": { "regexp": { "preset": "email" } } }
```

In the admin, pick one from **Pattern** in a text field's **Settings**.

## Dates

A `Date` field's `format` says what it holds, and how its value is written:

| `format`   | Value              | Entry form            |
| ---------- | ------------------ | --------------------- |
| `date`     | `2026-11-03`       | a date picker         |
| `datetime` | `2026-11-03T14:30` (seconds and a `Z` or `+01:00` offset optional) | date and time |
| `time`     | `14:30`            | a time picker         |

Without a format a Date takes any ISO 8601 date string, as before. Bound it with
`validations.dateRange` (`{ "min": "2026-01-01" }`), written in the same format. Time-only fields
can be read today and are accepted on write in the next release.

## Lists

An `Array` of `Symbol`, `Text`, `Integer`, `Number` or `Date` holds a list of those values, each
checked as one (`"items": { "type": "Integer" }`; a list of dates takes `items.format`). The entry
form edits it item by item, GraphQL types it as a list of the scalar (`[Int]`) and generated types
as `number[]` or `string[]`. Lists of `Text`, `Integer`, `Number` and `Date` can be read today and
are accepted on write in the next release; lists of `Symbol`, `Link` and `Component` work as before.

## Organizing the model

- **Group** files a type in the admin's sidebar under a heading (`Marketing`, `Docs`); types
  without one are listed first.
- **Description** says what the type is for, for editors choosing one and agents reading the model.
- **Icon** is a short name the admin draws beside the type (`newspaper`, `calendar`).
- **Layout** arranges the entry form into tabs, and fields within a tab into named groups, which
  can start collapsed. It is for editors only: nothing about storage, validation or delivery
  changes, and Delivery never serves it. Each field sits in one place; fields the layout doesn't
  place follow on the first tab, so a new field always shows up.

```json
{
  "group": "Editorial",
  "icon": "newspaper",
  "layout": {
    "tabs": [
      { "apiId": "content", "name": "Content", "groups": [{ "fields": ["title", "body"] }] },
      { "apiId": "seo", "name": "SEO", "groups": [{ "name": "Search", "fields": ["seo"], "collapsed": true }] }
    ]
  }
}
```

Set them in the content type dialog, or over the API and MCP (`model_create_content_type`); left
out of a save they stay as they are, and `null` clears one. Removing a field removes it from the
layout.

## Field guidance

Every field can carry plain-text guidance for whoever fills it, editor or agent:

| Attribute     | At most | Where it shows                                                        |
| ------------- | ------- | --------------------------------------------------------------------- |
| `help`        | 500     | Under the input on the entry form, and in the field's brief to AI     |
| `placeholder` | 200     | In the empty input; never stored as a value                           |
| `description` | 2000    | What the field means: read from the model by agents and API clients, and in the brief to AI |

Set them in the admin from a field's **Guidance** button in the content type dialog, or on the
field definition through the API or MCP (`model_create_content_type`). Agents get them with the
rest of the definition from `model_get_content_type`, and AI drafting and autofill write to them.
Generated TypeScript types carry a field's description (or help) as its doc comment.

## Conditional field rules

A field's `rules` hide or disable it while another field matches. A shipping address can show only
when the delivery method is `post`; a price can lock once the status is `sold`:

```json
{
  "apiId": "price",
  "name": "Price",
  "type": "Number",
  "rules": [{ "action": "disable", "when": { "field": "status", "operator": "eq", "value": "sold" } }]
}
```

- **`hide`**: the field leaves the entry form and isn't required. A value it already holds is kept,
  and comes back into view when the rule stops matching.
- **`disable`**: the field is read-only and keeps its stored value; a write that changes it is
  refused. A new entry's disabled field keeps its default (or stays empty).

`when.field` names a field beside this one, or a field inside a component beside it with a dot path
(`hero.style`). The operators are `eq` and `ne` (equal or not to a string, number or boolean), `in`
(one of a list), `empty` and `notEmpty`, and `gt` and `lt` (for a number field). Any matching rule
applies, up to ten per field. Inside a list of components, a field can be hidden per item but not
disabled.

Rules are judged on the values being written, the same way everywhere: the entry form hides and
locks fields as you type, and the API, MCP agents and AI drafting are held to them on save. AI
drafting and autofill never write a hidden or disabled field. Add rules in the admin from a field's
**Rules** button in the content type dialog, or on the field definition over the API and MCP.
Generated TypeScript types make a required field that a rule can hide optional.

Hide and disable are editorial aids, not access control: a hidden value is still stored and
delivered, and anyone who can write the entry can open a disabled field by changing the value its
rule reads. To keep a field from a role, use the role's field rules (denied or read-only fields,
see [Roles](/guides/api-keys/#roles)).

## Changing a model

- **Adding a field** is safe: existing entries simply have no value for it until edited. Make it
  optional first if entries already exist, then fill it (AI autofill can help, see
  [AI features](/guides/ai/)) before making it required.
- **Adding a block type**, or an optional field to one, is safe. **Removing a block type** is
  refused while any entry (a draft, the trash or a published version) still has a block of it;
  the error lists those entries, so change or remove their blocks first.
- **Removing a field**, at any depth (a component's field, a block type's field), is refused the
  same way while any entry still holds a value for it: the `409` lists each field and its entries
  (`details.fieldsInUse`). There is no override. Clear the value in those entries (save them
  without it), publish the ones that are live so the published version drops it too, and purge any
  in the trash; then remove the field.
- **Tightening a rule** (a Date's `format` or `dateRange`, an asset link's `assetMimeTypes`) is
  saved even when entries already hold values it refuses, and the response says how many under
  `warnings` (`{ field, entries, message }`). Each of those entries is refused on its next save
  until the value is changed.
- **Renaming** a field's name is safe; its `apiId` is what code depends on, so treat that as
  permanent.
- **Keep the model in a file.** `contentworker model export` writes it out, and `contentworker
  model apply --dry-run` shows what a changed file would add, change and remove before anything
  does; see the [command-line tool](/guides/cli/#the-content-model-as-code).
- **Cloning a type** copies its fields, display field and singleton flag under a new API ID and
  name, as a draft with no entries; its URL pattern stays behind, so two types never route the
  same paths. In the admin it is **Clone…** in the type's menu on the Content page; over the API
  `POST …/content-types/{apiId}/clone` with `{ apiId, name }`, over MCP `model_clone_content_type`.
- **Deleting a type** is refused, naming every reason, while anything depends on it: entries (the
  trash included), another type whose links are restricted to it (in a component or block too), a
  menu or slug redirect naming one of its entries, or its URL pattern (clear it first, so the
  site's routes change on purpose). `GET …/content-types/{apiId}/dependents` lists them. To delete
  a type with its entries, ask for it (`DELETE …/content-types/{apiId}?purge_entries=true`,
  `model_delete_content_type` with `purgeEntries`, or the checkbox in the admin's delete dialog,
  confirmed by typing the API ID): a background job moves each entry to the trash and deletes it
  permanently, keeping any that another type's published entry links to, and the type goes when
  none are left. That takes `content:write` and `content:publish` as well as `content:manage`.
  What became of the type is recorded on the job, as `config.typeDeletion` on `GET
  …/bulk/jobs/{id}` (`{ deleted: true }`, or `{ deleted: false, reason }`); the admin shows it on
  the job's card. A deleted type sends `content_type.deleted`.
- **Try risky changes in an environment.** Clone `main` into a `staging` environment, change the
  model there, point a preview at it, then merge it back. See
  [Environments](/guides/environments/).
