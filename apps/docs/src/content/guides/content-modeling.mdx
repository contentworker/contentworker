A content model is the set of content types in a space. You define it in the admin (**Content →
New content type**) or over the API and MCP. Good models describe content by what it
*is* (an article, an author, a promo block) rather than where it appears, so the same entry can
feed a website, an app, an email and an agent.

## Content types

A content type has:

- an **`apiId`**, the stable identifier the API and SDKs use (`article`), which never changes;
- a **name** people see (`Article`);
- a **display field**, the field used as each entry's title in lists, pickers and search results;
- an ordered list of **fields**;
- optionally a **URL pattern**, where its entries live on your site.

Creating or changing a content type makes a draft definition. Each revision bumps the type's
`version`; publishing marks that version live for authoring and delivery and emits a
`content_type.published` event, so integrations (generated types, caches) can react. The admin's
content type dialog publishes as it saves.

### URL pattern

A URL pattern is a path starting with `/` that says where a type's entries live on your site, for
example `/blog/{slug}`. Its placeholders are `{id}` (the entry id), `{locale}`, or the API ID of one
of the type's own `Slug` fields; anything else is refused. In the content type dialog it is the
**URL pattern** field; over the API and MCP it is `urlPattern` on `POST …/content-types` and
`model_create_content_type` (`null` clears it). When a publish changes a slug the pattern names on
an entry that was already published, contentworker writes a `301` from the old path to the new one;
see [Redirects](/guides/redirects/#redirect-slug-changes). A revision that removes a slug a kept
pattern names is refused.

## Field types

| Type        | Holds                                                | Value                          |
| ----------- | ---------------------------------------------------- | ------------------------------ |
| `Symbol`    | Short, single-line text: titles, names, labels       | string                         |
| `Slug`      | A URL-safe identifier, normalized as you type        | string                         |
| `Text`      | Long, multi-line plain text                          | string                         |
| `RichText`  | A structured document: headings, lists, tables, links, embeds | object                |
| `Integer`   | A whole number                                       | integer                        |
| `Number`    | A decimal number                                     | number                         |
| `Boolean`   | Yes or no                                            | boolean                        |
| `Date`      | A date or date and time                              | ISO 8601 string                |
| `Location`  | A point on a map                                     | `{ "lat": …, "lon": … }`       |
| `JSON`      | Free-form structured data                            | object                         |
| `Link`      | A reference to an entry or an asset                  | `{ "id": …, "linkType": … }`   |
| `Component` | A group of nested fields (a "hero", a "call to action") | object                      |
| `Array`     | A list of `Symbol`, `Link` or `Component` items      | array                          |

Each field also says whether it is **required**, **localized** (a separate value per locale) and
**unique** (no two entries of the type may share a value; a clash is refused with the entry that
holds it). A field can carry a **default value** that new entries start with.

### Rich text

A `RichText` value is a document of nodes: paragraphs, headings, lists, quotes, code blocks, rules,
tables, links, embedded entries and assets, and external media embeds. Every write is checked
against that vocabulary, whoever makes it: an unknown node type is refused, a link must point at an
`http`, `https`, `mailto` or `tel` address (or a relative one), and a document may be at most
512 KiB and 64 levels deep.

An **embed** holds a video, a post or a track from an allowed provider: YouTube, Vimeo, X, Bluesky,
Mastodon, Spotify or SoundCloud. It is an `embed` node whose `data` is structured metadata, never the
provider's player HTML:

```json
{
  "nodeType": "embed",
  "data": {
    "url": "https://www.youtube.com/watch?v=dQw4w9WgXcQ",
    "provider": "youtube",
    "kind": "video",
    "title": "Never Gonna Give You Up",
    "authorName": "Rick Astley",
    "thumbnail": { "url": "https://i.ytimg.com/vi/dQw4w9WgXcQ/hqdefault.jpg", "width": 480, "height": 360 },
    "width": 200,
    "height": 113,
    "aspectRatio": 1.7699
  },
  "content": []
}
```

Only `url` (https) and `provider` are required. Paste a provider URL into the rich-text editor and it
becomes an embed with a preview card; the editor fills the rest by calling
`POST /spaces/<space>/environments/<env>/embeds/resolve` (the `embed_resolve` MCP tool), which asks
the provider's oEmbed endpoint and returns only these fields. A URL that isn't https or isn't on an
allowed provider is refused. Imported HTML keeps provider players, tweet blockquotes and WordPress
embed blocks as embeds, with the URL and provider only.

Your front end decides how an embed looks: a player built from `provider` and `url` (for example
`https://www.youtube-nocookie.com/embed/<id>` in an `<iframe>` sized by `aspectRatio`), or the safe
default, a link card with the thumbnail and title, which `embedCard` in `@contentworker/sdk-core`
builds for you. A `mastodon` embed's host is whatever instance the author named, so don't frame it
in a player unless that instance is on your own list; the link card is always safe.

### Components and repeaters

A `Component` field groups nested fields that belong together: a hero block's heading, image and
button. An `Array` of components is a **repeater**: a list of feature cards, FAQ items or table
rows that editors add, remove and reorder.

The admin's content type dialog can't author a `Component` field, because it has no way to define
the nested fields: create one with the API (`POST …/content-types`) or the
`model_create_content_type` MCP tool. Existing component fields load and edit in the dialog.

Nested fields are ordinary fields, with three exceptions. They can't be localized on their own
(localization is decided once, on the field holding the component), they can't be unique, and they
can't be slugs. Components nest up to three levels; anything deeper is usually better as its own
content type, linked.

### Blocks

A **blocks** field is a list whose items can each take a different shape: a landing page body made
of a hero, then a section of rich text, then a call to action, in whatever order the editor picks.
It is an `Array` of `Component` that lists **variants** instead of one set of fields. In the
content type dialog, pick **Blocks** as the field's type, then add a block type for each shape
(a name, an API ID and its fields). In the entry editor, **Add block** offers those types; blocks
reorder and remove like repeater items.

Over the API or MCP, declare `items.variants` in place of `items.fields`:

```json
{
  "apiId": "body", "name": "Body", "type": "Array", "localized": false, "required": false, "position": 2,
  "items": {
    "type": "Component",
    "variants": [
      { "apiId": "hero", "name": "Hero", "fields": [
        { "apiId": "heading", "name": "Heading", "type": "Symbol", "localized": false, "required": true, "position": 0 }
      ] },
      { "apiId": "cta", "name": "Call to action", "fields": [
        { "apiId": "target", "name": "Target", "type": "Link", "linkType": "Entry", "localized": false, "required": false, "position": 0 }
      ] }
    ]
  }
}
```

Each stored block names its variant in `_type` and carries a `_key` the server assigns when the
entry is saved: `{ "_type": "hero", "_key": "0192f4a1-…", "heading": "Spring launch" }`. Send
existing blocks back with their `_key` and they keep it, so a front end can use it as a stable
identity across reorders. A variant's fields follow the component rules above. For a slot that
holds at most one block, set `validations: { size: { max: 1 } }` on the field. Links inside
blocks resolve with `include` like any other, GraphQL types the field as a union with one type per
variant, and the generated TypeScript types narrow on `_type`.

### References

A `Link` field points at an entry or an asset; an `Array` of links holds several. Restrict which
content types a link may target with `linkContentTypes`. Publishing an entry checks that
everything it links to exists, and an entry other published entries link to can't be permanently
deleted until those links are removed.

## Validations

| Validation          | Applies to                 | Checks                                       |
| ------------------- | -------------------------- | -------------------------------------------- |
| `in`                | Symbol, Text, Integer, Number | The value is one of a list               |
| `regexp`            | Symbol, Text               | The value matches a pattern                  |
| `range`             | Integer, Number            | The value is between a min and a max         |
| `size`              | Symbol, Text, Array        | Length, or number of items, is within bounds |
| `linkContentTypes`  | Link, Array of Link        | The linked entry is one of these types       |

Validations run on every write, from every surface: the admin, the API, imports, AI drafting and
agents. An AI agent can't save an entry a person couldn't.

## Changing a model

- **Adding a field** is safe: existing entries simply have no value for it until edited. Make it
  optional first if entries already exist, then fill it (AI autofill can help, see
  [AI features](/guides/ai/)) before making it required.
- **Adding a block type**, or an optional field to one, is safe. **Removing a block type** is
  refused while any entry (a draft, the trash or a published version) still has a block of it;
  the error lists those entries, so change or remove their blocks first.
- **Removing a field**, at any depth (a component's field, a block type's field), is refused the
  same way while any entry still holds a value for it: the `409` lists each field and its entries
  (`details.fieldsInUse`). There is no override. Clear the value in those entries (save them
  without it), publish the ones that are live so the published version drops it too, and purge any
  in the trash; then remove the field.
- **Renaming** a field's name is safe; its `apiId` is what code depends on, so treat that as
  permanent.
- **Keep the model in a file.** `contentworker model export` writes it out, and `contentworker
  model apply --dry-run` shows what a changed file would add, change and remove before anything
  does; see the [command-line tool](/guides/cli/#the-content-model-as-code).
- **Try risky changes in an environment.** Clone `main` into a `staging` environment, change the
  model there, point a preview at it, then merge it back. See
  [Environments](/guides/environments/).
