title: Blocks from code
description: Describe the components your site renders as JSON manifests, and push them as the block types of your pages' blocks fields with contentworker blocks push.
---

A page is an entry with a [blocks field](/reference/field-types/#blocks): an ordered list of blocks,
each one of the field's block types. With blocks from code, the block types come from your site's
code rather than the content model editor. You describe each component your front end renders in a
**manifest**, push the set of them (the **block catalog**) with the CLI, and ContentWorker makes
them the block types of the fields you name. Editors then compose pages from exactly what your
code can render.

A manifest is data: JSON, never a function. Nothing you push runs on the server or in the admin,
so a catalog can be checked, compared with the last one, versioned and shown without running
anyone's code. Placement rules are declarative too.

## Before you start

- Pushing a catalog changes the content model, so it needs `content:manage`; publishing the
  changed types (the default) needs `content:publish` too, as publishing a type always does
  (`--no-publish` pushes draft revisions with `content:manage` alone). Reading the catalog, its
  versions and its usage needs `preview:read`. See [API keys and access](/guides/api-keys/).
- Each target field must already exist: a top-level blocks field (an Array of Component with block
  types) on a content type. Create it once in the content model, or with
  [`contentworker model apply`](/guides/cli/#the-content-model-as-code), with any block type;
  the push replaces its block types with the catalog's.
- Each environment has its own catalog. Push to `staging` first with `-e staging`.

## The blocks file

`contentworker blocks push` reads `contentworker.blocks.json` from the working directory, or the
file you name. It is JSON, or a TypeScript or JavaScript module whose default export is the same
object.

```json
{
  "targets": [{ "contentTypeApiId": "page", "field": "sections" }],
  "blocks": [
    {
      "id": "hero",
      "name": "Hero",
      "group": "Headers",
      "thumbnail": { "assetId": "019a6b2e-5c4d-7e8f-9a0b-1c2d3e4f5a6b" },
      "fields": [
        { "apiId": "heading", "name": "Heading", "type": "Symbol", "required": true },
        {
          "apiId": "tone",
          "name": "Tone",
          "type": "Symbol",
          "validations": { "in": ["light", "dark"] }
        }
      ]
    },
    {
      "id": "grid",
      "name": "Card grid",
      "fields": [{ "apiId": "title", "name": "Title", "type": "Symbol" }],
      "slots": [{ "apiId": "cards", "name": "Cards", "allowedChildren": ["card"], "min": 1, "max": 6 }]
    },
    {
      "id": "card",
      "name": "Card",
      "allowedParents": ["grid"],
      "fields": [{ "apiId": "title", "name": "Title", "type": "Symbol" }]
    }
  ]
}
```

`page.sections` stands for a field of your own. A target must be a top-level Blocks field (an Array
of components with block types), not a Rich text field: pointing at one is refused with
`targets[0]: page.body is not a blocks field (an Array of Component with items.variants)`. The
admin's Build › Blocks screen fills its copy of this example with the first Blocks field in your
space.

Each target names a content type and one of its top-level blocks fields. Its top level takes every
block without `allowedParents`, or only the blocks a target lists in `blocks`. The catalog owns the
whole field: a block type the field had that the catalog doesn't provide is removed.

## A block's manifest

| Key              | Meaning                                                                                                   |
| ---------------- | --------------------------------------------------------------------------------------------------------- |
| `id`             | Stable identity, stored on each block as `_type`. A letter, then letters, digits or `_`. Never reused      |
| `name`           | What editors see. Change it freely: content never depends on it                                           |
| `group`          | The heading the block is listed under                                                                     |
| `description`    | Up to 1,000 characters                                                                                    |
| `thumbnail`      | `{ "assetId": "…" }` for an asset in the environment; the CLI imports `{ "url": "https://…" }` or `{ "file": "…" }` as one (see [Thumbnails](#thumbnails)) |
| `aliases`        | Ids the block had before (see [Renaming a block](#renaming-a-block))                                      |
| `fields`         | The block's props, as [field definitions](/reference/field-types/)                                         |
| `slots`          | Named places that hold other blocks                                                                       |
| `allowedParents` | The only blocks whose slots may hold this one; such a block never goes at a target's top level            |
| `responsive`     | Props that take a different value from a breakpoint up (see [Per-breakpoint overrides](#per-breakpoint-overrides)) |

A catalog holds at most 200 blocks, a block at most 10 slots, and the catalog at most 1,000,000
characters as JSON. A thumbnail URL must be `https` without credentials; data URLs and inline
markup are refused, and an `assetId` must name an asset in the environment.

### Thumbnails

The admin shows a block's thumbnail beside its name wherever editors pick a block: the canvas dock,
the entry form's Add block menu and Build → Blocks. It draws only `{ "assetId": "…" }` thumbnails,
because it loads images only from its own origin. So give the image however is handy, and
`contentworker blocks push` makes it an asset:

```json
{ "id": "hero", "name": "Hero", "thumbnail": { "url": "https://cdn.example.com/blocks/hero.png" }, "fields": [] }
{ "id": "quote", "name": "Quote", "thumbnail": { "file": "thumbs/quote.webp" }, "fields": [] }
```

- `{ "url": "…" }` must be `https` (a redirect must stay `https`); `{ "file": "…" }` is a path from
  the blocks file's folder.
- The image must be AVIF, GIF, JPEG, PNG, SVG or WebP (the response's `Content-Type`, or the
  file's extension) and at most 2 MiB. Anything else stops the push with `thumbnail_refused`,
  naming the block, before anything is uploaded or pushed.
- The CLI hashes each image (SHA-256) and looks for an asset with those bytes
  (`GET …/assets?contentHash=`). It reuses one it finds; otherwise, once the push is confirmed, it
  uploads the image as a draft asset named `<block>-thumbnail.<ext>`. Pushing again reuses that
  asset rather than uploading the image again. (An asset's hash is written a few seconds after its
  upload, so a push straight after another may upload a copy, which the library marks as a
  duplicate.)
- The catalog stores `{ "assetId": "…" }`, so thumbnails are versioned with it, and `--dry-run`
  uploads nothing: it lists the images it would import.
- Importing needs `assets:read` (the lookup) and `assets:write` (the upload) beside the push's
  own scopes; `preview:read` and `content:write` grant them.

The server never fetches a thumbnail. It still accepts a `{ "url": "…" }` that another client
pushes, keeping it for that tooling, but the admin lists such a block by its name. A thumbnail whose
asset is archived, deleted or not an image shows the name too.

### Props

Props use the content model's field vocabulary, with the rules any field inside a block follows
(no localized, unique or Slug fields; components nest at most three levels among themselves, and
a component prop counts toward the block depth below). `localized`, `required`
and `position` may be left out: they default to `false`, `false` and the field's place in the list.

Styling is design tokens, never raw CSS. A style prop is a Symbol with `validations.in`, such as
`tone: light | dark` or `size: sm | md | lg`. A JSON prop is refused, and so is a prop named
`style`, `styles`, `css`, `class`, `className`, `classes` or `inlineStyle` unless it is such an
enumeration.

### Slots and placement

A slot becomes a nested blocks field of the block, with the slot's `apiId`, holding the blocks its
`allowedChildren` names. `min` above 0 makes the slot required, and `min` and `max` bound how many
blocks it holds.

- Every block a slot or `allowedParents` names must be in the catalog.
- The two sides agree: when a block lists `allowedParents`, each parent must have a slot that
  allows it, and no slot may allow it from a parent the list leaves out.
- A block can't end up inside itself, directly or through other blocks.
- Slots nest at most five levels below the page: the page's blocks field counts as 1, so a block
  can sit six deep (a section's rows' columns' stacks' groups' cards). A component prop counts its
  level too, so a block at the sixth level can't have one. A deeper chain is refused, naming its
  path (`page.sections[a].s[b].s[c].s[d].s[e].s[f].s`).
- Every slot is expanded in place, so a block allowed in many slots is repeated in the content
  type once per place. A target that would expand past 1,000 blocks, or past 1 MB of fields, is
  refused: allow fewer children per slot.

The push answers `422` naming each problem by its place in the file (`blocks[hero].fields.tone`,
`blocks[grid].slots.cards.allowedChildren`), all of them at once.

## Per-breakpoint overrides

A token prop can take a different value from some screen width up: a hero that is `size: md` on
phones and `size: xl` on desktops, a grid with one column on phones and three from tablets, a
banner hidden on phones. Breakpoints are your site's CSS, so they are declared in the blocks file,
mobile-first, beside `blocks` and `targets`:

```json
{
  "breakpoints": [
    { "id": "md", "name": "Tablet", "minWidth": 768 },
    { "id": "lg", "name": "Desktop", "minWidth": 1280 }
  ],
  "targets": [{ "contentTypeApiId": "page", "field": "sections" }],
  "blocks": [
    {
      "id": "hero",
      "name": "Hero",
      "responsive": ["size", "hidden"],
      "fields": [
        { "apiId": "size", "name": "Size", "type": "Symbol", "validations": { "in": ["sm", "md", "xl"] } },
        { "apiId": "hidden", "name": "Hidden", "type": "Boolean" }
      ]
    }
  ]
}
```

- **Breakpoints.** An `id` is a letter, then letters, digits or `_`, and never `base`. `minWidth` is
  a whole number of CSS pixels from 1 to 10,000, strictly increasing down the list. At most 6. The
  bare prop applies below the first breakpoint; each breakpoint applies from its `minWidth` up until
  the next one overrides it. A push without `breakpoints` has none, and removes any the catalog had.
- **`responsive`.** Each name is a top-level prop of the block that is a token (a Symbol, Integer
  or Number with `validations.in`) or a Boolean. Anything else is refused by its place in the file
  (`blocks[hero].responsive[1]`). A block without `responsive` takes no overrides.

The push writes the breakpoints onto each target field (`items.breakpoints`; the blocks fields in
its blocks' slots take the same ones) and `responsive` onto each block's variant, so an entry save
is checked against the content type alone. A content type the catalog doesn't target has no
breakpoints and keeps no overrides.

### How they are stored

Overrides sit beside the props, in `_responsive`, keyed by breakpoint id:

```json
{
  "_type": "hero",
  "_key": "…",
  "size": "md",
  "_responsive": { "lg": { "size": "xl" }, "md": { "hidden": false } }
}
```

The bare prop stays the base, required as before, so a frontend that knows nothing of breakpoints
renders the base and keeps working. `_responsive` isn't localized; an empty map, or a breakpoint
with no props, is removed on save. Delivery serves `_responsive` as stored, and only on blocks
someone gave an override. In GraphQL, a block with responsive props has a `_responsive` field
(`PageSectionsHeroResponsive`), one nullable field per breakpoint holding the props, a value that
isn't one of its prop's tokens served as `null`. An `update`
[block patch](/reference/field-types/#blocks) sets or unsets `_responsive` as a whole.

### Editing them in the admin

On the canvas, the width control above the page offers **Base** (390px, or just under a first
breakpoint that starts at 390 or below; with a first breakpoint from 1px no width shows Base, but
its preset still edits the bare props) and one width per
breakpoint at its `minWidth`, named by its `name`; a catalog without breakpoints keeps Desktop,
Tablet and Phone. With breakpoints the canvas always opens on Base, so its first edit sets the bare
prop; choose a breakpoint's width to override it there. The width in view is the breakpoint the inspector's **Look** tab edits: at Base it
sets the bare prop; at a breakpoint, a prop in the block's `responsive` shows the value it inherits
and where from ("From Base", "From Tablet") until you give it one there, which is marked "Set for
Tablet" with **Reset** to inherit again. A prop not in `responsive` reads "Same at every width" and
is edited at Base. Each change is an ordinary canvas edit (it undoes and saves with the draft), and
a breakpoint left with no overrides, or a block left with none, drops the key. Layers marks a block
that carries overrides. The entry form shows a block's overrides read-only under its props, with a
link to the canvas, and keeps them as they are when it saves.

A canvas undo can reach back past a save (a block removed and saved, then put back). The canvas
drops the overrides the content type no longer takes before it sends a save (reading the type again
when the server refuses one it still held), as the save would drop them. Any client's save is also
judged against the version before the stored one, so overrides an undo across one save brings back
count as carried even when a push made them stale meanwhile.

### Stale overrides

A push can remove a breakpoint, remove a prop from `responsive`, or narrow a prop's `in` (or
retype it), while entries still hold overrides for it. Those overrides are stale. They never fail
a save: each entry drops them on its next save, the way a renamed block takes its new id, and
reads serve them as stored until then. The push (and its dry run) reports them in
`staleOverrides`, by content type, block, breakpoint and prop, with how many blocks and entries
carry one (the current version of each entry outside the trash, up to 2,000 entries per type;
`complete: false` past that); it doesn't refuse the push. Editing the content type by hand
reports them the same way, as `warnings`. A
[promotion](/guides/environments/#promote-changes-to-the-live-environment) whose content types or
catalog would make the target's overrides stale waits for approval, saying how many blocks and
which breakpoints and props (entries the promotion itself writes over don't count), and so does
one whose entries carry overrides the target's type doesn't declare, which their copies there
lose.

An undeclared override is only stale when the entry already had it. In an edit (a create, an
update, a block patch, an import, and an import's analysis), an override of `base`, of a
breakpoint the field doesn't
declare, or of a prop not in the block's `responsive` is refused with `422` and the code
`override_undeclared`, naming the block and breakpoint (`sections[0]._responsive.xl`); a value its
prop doesn't take is refused as `override_invalid` (`sections[0]._responsive.lg.size`). Unless the
version the edit replaces already holds an override of that block type, breakpoint and prop (with
that value), in any field or locale: then it was carried, by moving, duplicating or copying a
block, undoing a change or sending the entry back, and the save drops it. So a typo is caught, and
stored overrides never block a save. Copies (snapshot restores, clones, promotions, version
restores) carry what was stored and aren't judged; an environment merge drops the overrides the
target's type doesn't take before it stores the entry.

## Renaming a block

A block's `name` can change at any time. To change its `id`, give the new block the old id in
`aliases`:

```json
{ "id": "banner", "name": "Banner", "aliases": ["hero"], "fields": [...] }
```

The push reports it as renamed rather than removed and added, and nothing is stranded: blocks
stored as `"_type": "hero"` keep validating and reading as `banner` in the editor, and each takes
`banner` on its entry's next save. GraphQL serves them as `banner` right away. The REST Delivery and
Preview APIs return each block as stored, so until an entry is saved again a block can still
carry the old id: give the [renderer](#rendering-blocks) the catalog, and it renders such a block
as `banner`.

A former id is never reused: a push that brings `hero` back as a different block while the catalog
in force lists it as an alias is refused. Removing a block outright and later pushing a new one
under its id isn't detected, so pick a new id.

## Push the catalog

```sh
contentworker blocks push --dry-run -e staging
contentworker blocks push --yes -e staging
```

The CLI asks the server for a dry run and prints what would change: blocks added (`+`), changed and
renamed (`~`) and removed (`!`), then each content type and field it changes. Then it pushes,
against the version it showed: if someone else pushed in between, the push is refused rather than
overwriting theirs.

| Flag                  | Does                                                                         |
| --------------------- | ---------------------------------------------------------------------------- |
| `--dry-run`           | Show the change and push nothing                                             |
| `--allow-destructive` | Push a catalog that removes blocks or block props                            |
| `--no-publish`        | Leave each changed content type as a draft revision instead of publishing it |
| `--yes`               | Don't ask (required when not on a terminal)                                   |

A push that removes a block type or a prop is refused with exit code 4 unless you pass
`--allow-destructive`. A push that removes something an entry still holds (its current version,
a version in the trash, or its published version) is refused whatever the flags, naming the
entries: change those entries first, or keep the old id in `aliases` if it is a rename.

Each changed content type is revised with the content model's own checks and, unless
`--no-publish`, published. Every changed type and the new catalog version are written together, so
a push lands whole or not at all.

## Rendering blocks

`@contentworker/sdk/react` has `<Blocks>` and `@contentworker/sdk/vue` has `<CwBlocks>`: give
either a blocks field's value and a component for each block id, and it renders each block with
its component, in order, keyed by its `_key`, inside one element (`as`, a `div` by default, which
takes the other attributes you give). A block's slots render with the same components.

Generate the types first. `contentworker types` types each block from the catalog in force
(`BannerBlock`, `GridBlock`, …, a slot typed as a list of the blocks it allows) and maps every id
to its type in `BlockTypes`:

```sh
npx contentworker types --out src/generated/content-types.ts
```

```tsx
import { type BlockComponents, Blocks, type DeliveredEntry } from '@contentworker/sdk/react';
import type { BlockTypes, PageFields } from './generated/content-types';
import catalog from '../contentworker.blocks.json';

const components: BlockComponents<BlockTypes> = {
  banner: ({ block, attrs, fieldAttrs }) => (
    <section {...attrs}>
      <h1 {...fieldAttrs('heading')}>{block.heading}</h1>
    </section>
  ),
  grid: ({ block, attrs, slots }) => (
    <section {...attrs}>
      <h2>{block.title}</h2>
      {slots.cards({ as: 'ul', className: 'cards' })}
    </section>
  ),
  card: ({ block, attrs }) => <li {...attrs}>{block.title}</li>,
};

export function Page({ entry }: { entry: DeliveredEntry<PageFields> }) {
  return <Blocks value={entry.fields.sections} components={components} catalog={catalog} as="main" />;
}
```

Each component gets:

| Prop         | Is                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------- |
| `block`      | The block, typed by `BlockTypes`, with `_type` its current id                               |
| `slots`      | A function per slot, rendering its blocks in an element: `slots.cards({ as: 'ul' })`         |
| `attrs`      | Spread onto the block's root element. Empty, except in a [preview](#in-a-live-preview)       |
| `fieldAttrs` | `fieldAttrs('heading')`, spread onto the element showing that field. Empty, except in a preview |
| `ghost`      | In a live preview, `inserted`, `changed` or `removed` for a block Coworker proposes          |
| `index`      | Its place among its siblings                                                                |
| `responsive` | Its [per-breakpoint overrides](#per-breakpoint-overrides), stale ones left out              |

- **Renamed blocks.** For a field the catalog targets, pass `catalog` (your blocks file, or what
  `GET …/block-catalog` answers); for any other blocks field, its `variants` from its content type.
  A block stored under a former id then renders with the component for its current one, its
  `block._type` set to that id.
- **Unknown blocks.** A block no component is given for (one a newer catalog added, say) renders
  with `fallback` if you pass one, else not at all. A value that isn't a block (no `_type`) is
  skipped; a value that isn't a list renders the empty element.
- **Slots.** A slot holding nothing still renders its element, so the canvas has somewhere to offer
  a seam.
- **Server components.** `<Blocks>` uses no hooks, so it renders in a server component, and so do
  the block components it renders. `slots` and `fieldAttrs` are functions, which can't be passed to
  a `'use client'` component: put the client parts inside a block's component instead.

In Vue, a block's component declares a `block` prop (or reads it from `useBlock()`), and its slots
are Vue slots, with `as` and attributes as slot props. The block's preview marks fall through onto
its root element, and `useBlock()` gives `block`, `ghost`, `index` and `fieldAttrs`:

```vue
<!-- Grid.vue -->
<script setup lang="ts">
import { useBlock } from '@contentworker/sdk/vue';
import type { GridBlock } from './generated/content-types';
defineProps<{ block: GridBlock }>();
const { fieldAttrs } = useBlock<GridBlock>();
</script>

<template>
  <section>
    <h2 v-bind="fieldAttrs('title')">{{ block.title }}</h2>
    <slot name="cards" as="ul" class="cards" />
  </section>
</template>
```

```vue
<CwBlocks :value="entry.fields.sections" :components="{ banner: Banner, grid: Grid, card: Card }" :catalog="catalog" as="main" />
```

Vue needs a slot's name before it renders, so it knows a slot from the catalog or variants, or
from the blocks it holds: pass one of them for empty slots to render.

For another framework, or a renderer of your own (strings, DOM nodes), `@contentworker/sdk/blocks`
does the same with plain functions. `renderBlocks` calls one per block id and returns the results
with the top level's marks; `resolveBlocks` returns the resolved tree to walk yourself.

```ts
import { renderBlocks } from '@contentworker/sdk/blocks';

const escapeHtml = (text: string) =>
  text.replace(/[&<>"']/g, (c) => `&#${c.charCodeAt(0)};`);

const { items } = renderBlocks<BlockTypes, string>(entry.fields.sections, {
  catalog,
  components: {
    banner: ({ block }) => `<section><h1>${escapeHtml(block.heading)}</h1></section>`,
    grid: ({ slot }) => `<ul>${slot('cards').items.join('')}</ul>`,
  },
});
```

### Per-breakpoint values

Each resolved block carries `responsive`: its overrides in breakpoint order, with any the catalog
no longer declares left out, and, when the catalog's blocks (or the `variants`) carry their
`fields`, any value that isn't one of its prop's tokens. `responsiveProp(block, prop, catalog)`
reads one prop at every width, `{ base: 'md', lg: 'xl' }`. Applying it is your CSS: a class per
breakpoint, a custom property per media query, or a container query. A server-rendered page can't
know the screen's width, so the SDK never picks one value.

Treat an override value as you treat the bare prop: match it against the token list before it goes
into a class name, a `style` attribute or any other markup, never interpolate it as it is.
Delivery serves `_responsive` as stored, so a value written by hand, or one a later push narrowed
out, reaches a page until the entry is saved again.

```tsx
import { responsiveProp } from '@contentworker/sdk/react';

const sizeClasses = (block: HeroBlock) =>
  Object.entries(responsiveProp(block, 'size', catalog))
    .map(([bp, size]) => (bp === 'base' ? `size-${size}` : `${bp}:size-${size}`))
    .join(' ');
```

`contentworker types` types each block's `_responsive` (`readonly lg?: { readonly size?: 'sm' |
'md' | 'xl' }`) and exports `breakpoints`, the list as declared. For a blocks field the catalog
doesn't target, pass `variants` and `breakpoints` (the field's `items.breakpoints`) instead of
`catalog`.

### In a live preview

Pass `preview`, the field as a [live preview](/guides/live-preview/) ref (a `field` that isn't a
field path, such as `sections]`, is refused with an error), and every block, slot and
field carries the marks the admin selects and draws seams from: `data-cw-ref` on each block
(`sections[<key>]`) and field (`sections[<key>].heading`), and `data-cw-slot` on the element holding
each slot's blocks (`sections`, `sections[<key>].cards`). Pass `ghosts` (`view.ghosts`) and a
proposed block also carries `data-cw-ghost`, to style it by. Without `preview`, nothing is marked,
so the same components ship to production.

```tsx
<Blocks
  value={live.entries[entry.id]?.view.withProposals.sections ?? entry.fields.sections}
  components={components}
  catalog={catalog}
  ghosts={live.entries[entry.id]?.view.ghosts}
  preview={
    live.active && {
      space: 'your-space',
      environment: 'main',
      entryId: entry.id,
      contentType: entry.contentType,
      locale: 'en-US',
      field: 'sections',
    }
  }
/>
```

## Versions

Every push that changes something stores a new version: version 1 first, then one more each time,
with who pushed it, when, and which blocks it added, changed, removed and renamed. A version also
carries a hash of its blocks, targets and breakpoints, so pushing the catalog in force again
changes nothing and writes nothing: it is safe to run `blocks push` on every deploy. A changed
breakpoints list is a change (`changes.breakpoints: true`), and so it is for an environment
compare and a promotion, which copies the breakpoints with the catalog.

## Block usage

`GET …/block-catalog/usage` (and the MCP tool `blocks_usage`) counts how many entries use each
block, in all and per content type: the current version of each entry outside the trash, once per
entry however often it uses the block, a block stored under a former id counting as its block.
Content types you can't read are left out. The count reads up to 2,000 entries per type; past that
`complete` is `false` and the counts are a lower bound.

## Narrowing blocks per environment

The code says what a page can be built from; an environment's block config says what its editors
may use of that. It only ever narrows: per target (the top level of a blocks field) and per block
slot, wherever that block is placed, it can

- allow fewer blocks (`blocks` for a target, `allowedChildren` for a slot): a subset of what the
  code allows;
- tighten the count (`min` no lower than the code's, `max` no higher);
- lock the slot (`locked: true`): its blocks can't be added, removed, moved or reordered, but
  what's inside them can still be edited.

```json
{
  "expectedVersion": 0,
  "targets": [{ "contentTypeApiId": "page", "field": "body", "blocks": ["hero", "grid"] }],
  "blocks": [
    { "block": "grid", "slots": { "items": { "allowedChildren": ["card"], "max": 3 } } },
    { "block": "footer", "slots": { "links": { "locked": true } } }
  ]
}
```

`PUT …/block-config` replaces the whole config (`content:manage`), checked against the catalog in
force: a name the catalog doesn't have, or anything wider than the code, is a `422` naming the part
(`blocks[grid].slots.items.max`). Send the `version` you read as `expectedVersion`; another set
landing first is a `409`. `GET …/block-config` reads it, and `GET …/block-config/effective` answers
the rules every target and slot follows once the config is laid over the code.

Every save holds what it changes to the config: placing a block where it isn't allowed, or
changing a block's type under its key (`block_not_allowed_here`), changing a locked slot's blocks
(`slot_locked`), or taking a slot's count past its bounds (`slot_too_few`, `slot_too_many`) is a
`422`, whether the save comes from the editor, the API, MCP, a block patch or a CSV or JSON import
(whose analysis lists the records it would refuse). Content saved before the config stays
saveable as long as the save leaves those blocks where they are, and a slot over its new `max` can
shrink one block at a time. A locked page can still be filled in a locale it has no blocks in yet.
Snapshot restores, environment clones and promotions, and restoring an entry's earlier version
carry content as it is, so a restored version can bring back blocks from before a slot lock (a
[locked region](#locking-regions-of-an-entry) still holds a restore).

Exports, snapshot imports and environment clones carry the catalog in force and its config: the
copy starts its own history at version 1. An import leaves behind (and names in its report) a
config that doesn't fit the catalog; a clone carries it as the source has it, stale parts included
([Environments](/guides/environments/#export-and-import-a-snapshot)). A
[promotion](/guides/environments/#promote-changes-to-the-live-environment) copies them too, as a
push and a set of the target's own, and waits for approval whenever that changes which blocks go
where, a slot's counts or locks, or removes blocks from a type.

Pushing a new catalog is never blocked by the config. Parts of the config naming what the catalog
no longer has are listed as `stale` in the effective rules and ignored until the config is set
again; a renamed block keeps its narrowing.

### Setting it in the admin

Build → Blocks has a **Rules** card between the catalog's facts and its blocks, with one row per
place blocks go: each blocks field the catalog fills ("Page › Main") and each block's slot
("Grid › Items"). A row says what the code allows there and what editors may place now. With
`content:manage`:

- **Edit** opens the place's controls under its row: the blocks it takes, ticked from the code's
  list (at least one stays ticked), and **Fewest** and **Most**, blank for the code's own and
  refused past it.
- **Locked** is a switch on the row.
- **Save rules** sends the whole config with the version you started from. If someone else saved
  first, the card says so and shows their rules; make your change again over them. A refusal
  shows beside the control it names.

The card's header shows the config's version, and who set it when. Parts a newer push left stale
are listed as ignored; saving the rules removes them. Without `content:manage` the card reads only.

The card switches between three views (it opens on **Rules** each visit):

- **Rules**: the rows and their controls, above.
- **Code**: the config exactly as [`PUT …/block-config`](#the-api-and-mcp) takes it, the
  `{ targets, blocks }` of its body, as read-only JSON, with **Copy JSON**. It is normalized and in
  a stable order (the catalog's targets and slots, and each part's keys as the API returns them), so
  it diffs cleanly against a copy you keep. Ignored parts aren't in it.
- **Narrowed from code**: each place's rule from the code against the rule in force, as JSON in
  one shape (`blocks` or `allowedChildren`, `min`, `max`, `locked`). Only the places that differ
  are shown, and any with ignored parts, unless **Show all** is on. Side by side from tablet width
  (the code's on the left, marked −; in force on the right, marked +), one column on a phone.

While the Rules view has unsaved edits, Code and Narrowed from code show the draft, marked
**Unsaved**: Code is then the body Save rules will send, with the version it was edited from.

The editors follow the rules in force. On the canvas the dock offers only the blocks a slot's rule
takes, a locked slot draws no seams, and its blocks can't be moved, duplicated or removed (Layers
and the inspector show the lock). In the entry form, Add offers only the allowed blocks, and a
locked field or slot has no Add, move or Remove. Blocks stored before the rules stay, editable in
place. Both judge a save as the server will before sending it, and a refusal shows on the block,
slot or field it names. A lock holds only what is stored: a block placed in this edit, or a new
entry, is filled as it comes, as the server allows.

## Locking regions of an entry

The config's `locked` holds a slot on every entry of a type. To hold part of one entry instead (a
page's approved hero and legal footer, with the rest open), lock a region of its blocks: one block,
or a run of neighbouring blocks in one slot, named by their `_key`s.

```json
{
  "expectedVersion": 4,
  "locks": [
    { "field": "body", "keys": ["<hero key>"], "depth": "subtree" },
    { "field": "body", "keys": ["<legal key>", "<links key>"], "freeze": "all" }
  ]
}
```

`PUT …/entries/:id/block-locks` replaces the entry's whole list (a lock left out is unlocked) and
makes no version. `depth` is `subtree` (the blocks and everything inside them, the default) or
`self` (their own slots stay open); `freeze` is `structure` (no add, remove, move or swap; fields
stay editable, the default) or `all` (fields frozen too). The keys must be a run the entry holds,
and a block belongs to at most one region (`lock_overlaps`). Setting locks needs the `lock` action
on the entry's content type, which the Manager and Administrator roles hold; anyone with it may
unlock, whoever locked.

From then on a save that removes, swaps, reorders or splits a region's blocks, or inserts one among
them, is a `422` `region_locked`; with `subtree` so is any change to the blocks inside, and with
`freeze: 'all'` a change to a field is `region_frozen`. This holds with or without a block config,
from the editor, the API, MCP, a block patch or an import. A lock holds in every locale that has
its blocks. A lock whose blocks are gone is listed as `stale` and blocks nothing. Restoring an
earlier version keeps the locks held now and is held to them, unless you hold `lock` on the type
(you could lift the lock anyway); an environment clone carries them. A key two blocks hold can't
be locked (`lock_ambiguous`), and a save that gives a locked block's key to a second block is
refused. A lock on a field your role denies or makes read-only is yours neither to set nor lift. Delivery and
Preview never return locks. Every lock and unlock is in the audit log.

In the admin, lock from the canvas: select a block (shift-click a neighbour in Layers, or press
Shift with ↑ or ↓, to take a run of blocks in one slot), and in its settings choose **This block and
everything inside** or **Only this block**, tick **Also freeze the content** if its words should
stay as they are too, and press **Lock**. Lock and **Unlock** show only to someone holding `lock`
on the type, and wait for unsaved block changes to be saved (a lock names saved blocks). A locked
region has an outline with a lock on the page and a lock in Layers, with who locked it and when;
its blocks can't be moved, duplicated or removed, nothing can be added between or inside them, and
with the content frozen their settings read only. The entry form shows the same on the blocks'
cards. Stale locks are listed under the canvas's Checks, with **Clear**. A save the server refuses
for a region is said on the locked block.

## The API and MCP

| Method | Path                                 | Scope            | Does                                           |
| ------ | ------------------------------------ | ---------------- | ---------------------------------------------- |
| GET    | `…/block-catalog`                    | `preview:read`   | The catalog in force; `404` before the first push |
| POST   | `…/block-catalog`                    | `content:manage` (+ `content:publish` to publish) | Push `{ blocks, targets, breakpoints?, dryRun?, expectedVersion?, allowDestructive?, publish? }` |
| GET    | `…/block-catalog/versions`           | `preview:read`   | Versions newest first, without their blocks (`?limit`, `?before`) |
| GET    | `…/block-catalog/versions/:version`  | `preview:read`   | One version                                    |
| GET    | `…/block-catalog/usage`              | `preview:read`   | Entries using each block, per content type     |
| GET    | `…/block-config`                     | `preview:read`   | The block config; version 0 before the first set |
| PUT    | `…/block-config`                     | `content:manage` | Replace `{ expectedVersion, targets, blocks }` |
| GET    | `…/block-config/effective`           | `preview:read`   | Every target and slot's rules, and `stale` config parts |
| GET    | `…/entries/:id/block-locks`          | `preview:read`   | An entry's locked regions, and which are stale |
| PUT    | `…/entries/:id/block-locks`          | `content:write` + `lock` | Replace `{ locks, expectedVersion? }` |

`…` is `/spaces/:space/environments/:env`. A push answers what it did, or would do with `dryRun`:
`previousVersion`, `version`, `changes`, `contentTypes`, `destructive`, `inUse` (what it would
remove that entries hold), `staleOverrides` (overrides it strands) and `warnings`. Send the dry run's `previousVersion` as
`expectedVersion` to be refused (`409`) if another push lands first. A refused push carries the
same result in the error's `details`. From code, the management SDK has
`cma.blockCatalog.{get, version, versions, push, usage}`, `cma.blockConfig.{get, set, effective}`
and `cma.entries.blockLocks.{get, set}`
([SDKs](/guides/sdks/)).

Agents get the same through MCP: `blocks_catalog_get`, `blocks_catalog_versions`, `blocks_usage`,
`blocks_catalog_push` (with `dryRun`), `blocks_config_get`, `blocks_config_effective`,
`blocks_config_set`, `entries_block_locks_get` and `entries_block_locks_set`, under the same scopes ([MCP](/guides/mcp/)).

The admin's Build → Blocks screen lists the catalog in force, read-only, and sets the block config
([Setting it in the admin](#setting-it-in-the-admin)).
