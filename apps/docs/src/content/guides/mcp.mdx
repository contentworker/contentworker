title: MCP server
description: Connect Claude, ChatGPT, an IDE or your own agent to a workspace over the Model Context Protocol, with the same permissions as a person.
---

Every workspace serves an MCP server at `/mcp` (streamable HTTP), on the admin's own address for
clients that connect with OAuth and on its `api.` address for callers with a token. Its tools are the same
operations the REST API and the admin use, behind the same permission checks, so an agent can do
exactly what its token allows and nothing a person with that token couldn't.

## Connect with OAuth

MCP clients that support remote connectors (Claude, ChatGPT, MCP-capable IDEs) connect with just
the URL:

```
https://your-workspace.contentworker.app/mcp
```

The client discovers where to sign in, registers itself, and opens an approval screen on the
admin. If you aren't signed in, the admin's sign-in page comes first and brings you back. You see
which scopes the client asks for, pick the space it may work in (from the spaces you're on), and
approve. The connection acts with your role in that space. The token it receives is capped twice: at
what it asked for, and at what you hold. A client can never ask for `space:admin` or
`content:manage` this way. Tokens are short-lived and refresh on use; revoke a connection at any
time under **Settings → Access → Connected apps**.

Command-line clients that can't open a browser use the device flow: they print a code to enter on
an approval page on the admin, where you sign in and approve the same way.

When an admin turns your account off, resets your password or two-factor sign-in, or your identity
provider deactivates you, every connection you approved and every personal access token you made
stops working.

## Connect with a token

For CI, scripts and agents you run yourself, use a
[personal access token](/guides/api-keys/#personal-access-tokens) or a Management key with only the
scopes the agent needs:

```sh
claude mcp add --transport http contentworker https://api.your-workspace.contentworker.app/mcp \
  --header "Authorization: Bearer $CONTENTWORKER_TOKEN"
```

Most tools take `space` and `environment` arguments, so one connection can work across
environments its token can reach.

## Skills

The server also publishes MCP skills, short task guides a client can load before it works:
`model-content` (design a content model and get its types), `author-and-publish` (find, edit and
publish entries, releases, scheduled publishing, workflow runs) and `import-content` (map, dry-run,
run and publish an import).

## Working well with agents

- **Give each agent its own token**, with the narrowest scopes and a [role](/guides/api-keys/#roles)
  limited to the content types it works on. The audit log then says which agent did what.
- **Keep publishing with people.** An agent with `content:write` but not `content:publish` drafts,
  and a person publishes. AI changes that wait for review show up in
  [agent reviews](/guides/approvals/#agent-reviews).
- **Let it read the model first.** `model_typescript` returns the content model as TypeScript,
  which is the most compact way for an agent to learn your fields before it writes.
- **Point it at the docs.** `docs_search` and `docs_read` let an agent look up conventions with
  the token it already holds.
